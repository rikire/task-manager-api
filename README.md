Тестовое задание Skyeng (Backend): REST API для управления задачами и их статусами на Symfony 8.1,
PHP 8.4, PostgreSQL 18 и Docker Compose. Готово всё, что требует задание: каталог статусов (список,
чтение, создание, удаление), задачи (создание, чтение, список с фильтром по статусу, удаление, смена статуса).

Живые плашки: CI — результат последнего прогона на `main`; покрытие тестами и оценка мутационного
тестирования (MSI — доля намеренно внесённых в код ошибок, которые поймали тесты) — всего кода, их считает
CI после каждого слияния в `main` (`make badges`). Остальные — статические и ведут на файл, где закреплено
значение; правила с плашек (PHPStan, сложность, Deptrac, Psalm, формат коммитов) проверяет CI, нарушение
валит сборку.

## Как читать репозиторий

Здесь два проекта в одном: API по заданию и эксперимент с процессом разработки, в котором код пишет
ИИ-агент, а человек решает и принимает. Процесса заметно больше, чем нужно для девяти эндпоинтов, —
почему, рассказано в [предыстории](#предыстория-откуда-столько-процесса).

**Проверить задание:** [текст задания и что куда попало](docs/task/README.md) →
[быстрый старт](#быстрый-старт) → [эндпоинты](#эндпоинты) →
[архитектурные решения](#архитектурные-решения-и-компромиссы) → код в `src/` (модули `Task` и `Status`,
в каждом папка на сценарий) и тесты в `tests/` → [использование ИИ](#использование-ии) →
[что не сделано](#что-дальше).

**Разобраться в процессе:** [предыстория](#предыстория-откуда-столько-процесса) →
[docs/pre-init/README.md](docs/pre-init/README.md) (36 решений о процессе: что выбрано и почему; начать
с 01 — каркас процесса, 13 — что решает человек, 05 — TDD) → [AGENTS.md](AGENTS.md) (правила для агента,
у каждого — ссылка на решение) → одно изменение OpenSpec (единица работы: требования → тесты → код →
ревью) от начала до конца, например
[task-status-change](openspec/changes/archive/2026-10-07-task-status-change/): `proposal.md` (что и
зачем, допущения и вопросы), `specs/` (сценарии), `design.md`, `tasks.md`, `review.md` (сводка ревью для
человека) → [реестр сбоев агента](docs/registers/failures.md).

**Языки.** Документы для человека — на русском (README, архитектура, `docs/pre-init/`); то, что читает
агент, в том числе общие для агента и человека документы, — на английском: AGENTS.md, спеки OpenSpec,
ADR (Architecture Decision Record — запись архитектурного решения с вариантами), реестры долга и сбоев,
`docs/constraints.md` ([решение 23 о документации](docs/pre-init/23-documentation.md)). Полная карта
документов и префиксов ID — [docs/README.md](docs/README.md).

## Эндпоинты

| Метод и путь | Что делает |
|---|---|
| `GET /api/statuses` | список статусов |
| `GET /api/statuses/{id}` | один статус |
| `POST /api/statuses` | создать статус: `{"name": "code_review", "title": "Ревью кода"}` |
| `DELETE /api/statuses/{id}` | удалить статус: 409, если его используют задачи, и всегда для `new` |
| `GET /api/tasks` | список задач; фильтр `?status=<name>` |
| `GET /api/tasks/{id}` | одна задача |
| `POST /api/tasks` | создать задачу: `{"title": "…", "description": "…"}` (`description` необязательно), статус — `new` |
| `PATCH /api/tasks/{id}/status` | сменить статус: `{"status": "done"}` |
| `DELETE /api/tasks/{id}` | удалить задачу |

Точный формат запросов, ответов и ошибок — в контракте OpenAPI (`/api/doc` после запуска или
[docs/api/openapi.yaml](docs/api/openapi.yaml)).

## Быстрый старт

Нужны git и Docker с Compose v2 (amd64 или arm64).

```sh
git clone https://github.com/rikire/task-manager-api.git
cd task-manager-api
docker compose up -d
```

Первый запуск собирает образ приложения локально — несколько минут. Миграции применяются при старте
автоматически. Убедиться, что всё поднялось: `docker compose ps` — `db` и `app` в состоянии running,
`migrate` завершился с кодом 0. Остановить: `docker compose down` (с удалением данных — `down -v`).

- API: <http://localhost:8080>
- Документация и контракт OpenAPI: <http://localhost:8080/api/doc> (JSON — `/api/doc.json`); контракт
  генерируется из кода, его копия — [docs/api/openapi.yaml](docs/api/openapi.yaml); `make openapi-check`
  (в `make check` и CI) падает, если они разошлись

Если порт 8080 занят: `cp .env.example .env` и поменяйте `HTTP_PORT`. Файл `.env` читает Docker Compose,
приложение — нет; без него используются значения по умолчанию из `compose.yaml` (образец переменных —
[.env.example](.env.example)).

### Попробовать API

```sh
# Создать задачу: 201, статус new, в ответе id задачи
curl -s -i -X POST http://localhost:8080/api/tasks -H 'Content-Type: application/json' \
  -d '{"title": "Подготовить отчет", "description": "Отчет по продажам за май"}'

# Перевести задачу в done: 200; подставьте id из ответа выше
curl -s -i -X PATCH http://localhost:8080/api/tasks/<id>/status -H 'Content-Type: application/json' \
  -d '{"status": "done"}'

# Задачи со статусом done: 200, {"items": [...]}; несуществующий статус (?status=archived) — 422
curl -s -i 'http://localhost:8080/api/tasks?status=done'
```

Остальные эндпоинты и ошибки (неверные значения, лишнее поле, несуществующий id) —
[docs/api/curl-examples.md](docs/api/curl-examples.md).

## Архитектурные решения и компромиссы

- **Задача ссылается на статус внешним ключом, а в API статус передаётся по имени.** В базе
  `task.status_id → status.id`, поэтому задача не может остаться со статусом, которого нет, — это держит
  PostgreSQL, а не код. В запросах и ответах — `name` статуса (`"status": "done"`, `?status=done`), как в
  примерах задания. Статусы — пополняемый каталог; `new`, `in_progress`, `done` создаёт миграция, новая
  задача получает `new` ([ADR-0007](docs/adr/ADR-0007-api-conventions.md)).
- **Удаление статуса, который используют задачи, запрещено — 409, ничего не удаляется.**
  `new` удалить нельзя никогда: его получает каждая новая задача. Отвергнутые
  варианты — перевести задачи в `new` или удалить их вместе со статусом: оба меняют или теряют данные, о
  которых клиент не просил. Проверку делает модуль статусов через порт `StatusUsage`, а внешний ключ
  `ON DELETE RESTRICT` — последний рубеж: если задачу перевели в статус в момент удаления, ответ тот же 409
  (`REQ-STATUS-delete`, [ADR-0007](docs/adr/ADR-0007-api-conventions.md)).
- **Структура: два модуля, Task и Status; в каждом — ядро без фреймворка и папка на каждый сценарий.**
  Домен не знает о Symfony и Doctrine и обращается к базе через интерфейсы (порты); сценарий («создать
  задачу») — команда и обработчик в своей папке. Status не зависит от Task: «используют ли статус задачи»
  Status спрашивает через порт `StatusUsage`, который реализует Task. Правила слоёв проверяет Deptrac
  (статический анализ зависимостей между слоями) в `make check`. Цена — больше файлов, интерфейсы с одной
  реализацией, XML-мэппинг Doctrine вместо атрибутов; для девяти эндпоинтов такая структура избыточна,
  владелец принял эту цену ради ядра, независимого от HTTP и базы, и структуры, которую легко объяснить
  ([ADR-0006](docs/adr/ADR-0006-module-structure.md), [обзор архитектуры](docs/architecture/README.md)).
- **Строгий ввод, ошибки — в JSON с понятным кодом.** Битый JSON — 400; неверное значение, лишнее поле
  в теле и несуществующий статус (в теле `PATCH` и в `?status=`) — 422; несуществующий id и id не в формате
  UUID (в том числе UUID в верхнем регистре) — 404; занятое имя статуса — 409. Тело ошибки — формат
  problem details (RFC 9457) с полем `detail`, а для ошибок валидации — со списком `violations`.
  Неизвестные query-параметры игнорируются: их добавляют прокси и браузеры
  ([ADR-0005](docs/adr/ADR-0005-validation.md), [ADR-0007](docs/adr/ADR-0007-api-conventions.md)).
- **Переходы статусов свободные.** Задачу можно перевести из любого статуса в любой существующий, в том
  числе вернуть `done` в `new`: статусы — пополняемый каталог без заданного порядка, и задание правил
  переходов не задаёт. Повторная установка того же статуса — 200, задача не меняется, `updated_at` остаётся прежним
  (`REQ-TASK-status-change`).
- **Одновременная запись в одну задачу не защищена.** При двух одновременных `PATCH` побеждает последний;
  `PATCH`, совпавший по времени с `DELETE`, может ответить 200 уже удалённой задаче; два одновременных
  `DELETE` одного статуса могут оба ответить 204. Задание не требует гарантий при параллельной записи;
  защита — версия строки и 409 при конфликте — потребовала бы изменения схемы.
- **Сознательно упрощено.** Нет пагинации, авторизации и админки — задание их исключает
  ([вне рамок](docs/roadmap.md#вне-рамок)). Статус нельзя отредактировать: такого эндпоинта в задании нет.
  Списки упорядочены по id: это UUID v7, он растёт со временем, поэтому порядок — порядок создания.

## Использование ИИ

Код, тесты и документацию писал ИИ-агент Claude Code. Решал человек — владелец репозитория: требования,
контракт API и коды ошибок, схему данных, архитектурные решения (ADR), новые зависимости; каждый коммит
принят им. Граница «что решает агент, что человек» — в [AGENTS.md](AGENTS.md); коммиты, сделанные с
агентом, помечены трейлером `Assisted-by: Claude Code`.

Как проверялся результат:

- **Требования до кода.** Каждое поведение — изменение в OpenSpec (инструмент для требований: интервью,
  спеки со сценариями, задачи); отдельный агент без контекста разговора ищет в спеке двусмысленности до
  того, как человек её примет.
- **Тесты раньше кода.** Сначала падающие тесты на сценарии спеки, человек их принимает, потом код. Хук
  Claude Code (скрипт, который запускается на действие агента и может его заблокировать) не даёт агенту
  менять тесты, пока идёт реализация, — тест нельзя «подогнать» под код.
- **Автоматические проверки** из таблицы [ниже](#проверки-сверх-базовых-требований) — в pre-commit и CI;
  CI поднимает проект с чистого клона так, как это сделает проверяющий.
- **Приёмка человеком.** Перед коммитом отдельный агент сверяет изменение со спекой и пытается опровергнуть
  «готово»; агент пишет сводку ревью (упрощения, долг) и задаёт человеку 3–5 вопросов по изменению, чтобы
  проверить, что тот понимает код.
- **Ошибки агента** записываются в [реестр сбоев](docs/registers/failures.md) вместе с мерой, которая не
  даст им повториться.

В тексте задания был prompt injection — блок, адресованный не исполнителю, а ИИ-агенту. Он найден и
удалён из копии задания в репозитории ([docs/task/](docs/task/README.md)).

## Предыстория: откуда столько процесса

Перед этим заданием владельцу стало интересно, как вообще устроены проекты, где код пишет ИИ: какие
бывают подходы, что из них подкреплено данными, где агенты ошибаются. Исследование разрослось в проект
целого процесса и заняло большую часть времени ([сколько](#сколько-времени-ушло)). Это эксперимент
для изучения: процесс — источник идей для следующих проектов, а не шаблон, который стоит переносить
как есть.

Как шла работа:

1. **Исследование** — бриф и отчёт в [docs/pre-init/research/](docs/pre-init/research/README.md).
2. **36 решений о процессе** — [docs/pre-init/](docs/pre-init/README.md), 2026-10-05…06. Решения 01–30
   приняты до того, как было открыто задание, чтобы не подгонять процесс под него. 31–36 — после: что
   задание поменяло в процессе разработки (31), инструменты под стек (32), README (33), порядок
   внедрения (34), чек-лист инициализации (35), внешние ограничения и префиксы ID (36).
3. **Первый коммит** (2026-10-06) перенёс результат в репозиторий: решения, исследование, правила и
   хуки агента. Как они создавались, в истории git не видно.
4. **Инициализация** по [чек-листу](docs/pre-init/35-init-checklist.md): изменения `architecture-kickoff`
   (сценарии качества, ADR на стек и структуру) и `finish-init` (остальные проверки, скрипты и
   настройка; [архив](openspec/changes/archive/2026-10-07-finish-init/)). После инициализации
   `docs/pre-init/` заморожена (2026-10-07): новые решения о процессе — ADR, сбои и улучшения — в
   реестрах.
5. **Продукт** — изменения OpenSpec по одному: `status-catalog`, `task-crud`, `task-status-change`,
   `status-delete` ([роадмап](docs/roadmap.md#изменения), архив —
   [openspec/changes/archive/](openspec/changes/archive/)).

## Разработка

Предустановки: git, Docker, [mise](https://mise.jdx.dev) (ставит инструменты процесса по `mise.lock`),
make; для работы с агентом — Claude Code и gh. Песочница Claude Code на машине разработчика не
запускается и выключена; почему и как вернуть — `DEBT-001` в [реестре долга](docs/registers/debt.md).

```sh
make setup   # инструменты из mise.lock, git-хуки; безопасно запускать повторно
make dev     # стек для разработки: исходники смонтированы, есть dev-инструменты
make test    # только тесты
make check   # всё, что проверяет pre-commit (список — ниже)
make help    # все команды
```

После `make setup` один раз запустите `claude` в папке проекта и подтвердите доверие к ней — без этого
Claude Code не применяет настройки и хуки проекта.

Цели `test`, `check` и другие сами поднимают стек для разработки, если он не запущен.

Процесс работы над изменением: изменение в [OpenSpec](https://github.com/Fission-AI/OpenSpec)
(инструмент для требований: интервью, спеки, задачи) → тесты, которые сначала падают → реализация →
проверки → приёмка человеком и PR. В `main` вливается только PR с зелёным CI: `commits` проверяет
каждый коммит (формат, секреты, правила), `clean-clone` поднимает проект как проверяющий и прогоняет
`make check`.

### Проверки сверх базовых требований

Задание просит кратко обосновывать улучшения сверх базовых требований ([задание](docs/task/README.md);
внешнее ограничение `CON-DELIV-justify-extras` в [docs/constraints.md](docs/constraints.md)). Каждая
проверка ниже ловит то, что иначе осталось бы на внимательность человека или агента. Записи `IMP-…` —
в [реестре улучшений](docs/registers/debt.md).

| Проверка | Где | Зачем |
|---|---|---|
| PHP-CS-Fixer: стандарт Symfony, `strict_types` везде | `make check` | один стиль без споров; строгие типы на границах вызовов |
| PHPStan max: типы, мёртвый код, пустой и «проглатывающий» `catch` (в том числе своё правило) | `make check` | ошибки типов и тихо потерянные ошибки находятся до запуска ([правила кода](.claude/rules/code.md)) |
| Deptrac: правила слоёв и модулей | `make check` | контроллеры не ходят в базу, модуль Status не зависит от Task ([ADR-0006](docs/adr/ADR-0006-module-structure.md)) |
| Когнитивная сложность методов и классов | `make check` | метод сложнее 5 или класс сложнее 20 валит сборку: длинный запутанный код не проходит (`QAS-MAINT-readability`) |
| Psalm, taint-анализ | CI, блокирует | ввод из запроса не должен доходить до SQL, HTML или shell |
| Infection по изменённым строкам PR | CI, только отчёт | показывает, какие изменения кода тесты не замечают (`IMP-008`) |
| Покрытие и MSI всего кода (`make badges`) | CI, только отчёт; с `main` публикуется в ветку `badges` | живые цифры на плашках README: видно, насколько тесты покрывают код и ловят ошибки, без внешних сервисов |
| Аудит зависимостей (`composer audit`) | `make check` | известные уязвимости в пакетах |
| Роадмап и порядок изменений | `make check` | статусы в [роадмапе](docs/roadmap.md) совпадают с изменениями OpenSpec; нельзя начать изменение, пока выше в роадмапе не завершено изменение с приоритетом «обязательно» |
| Форма изменений, сводок ревью и ADR | `make check` | у изменения — таблица покрытия и списки «подтверждено / допущения / открытые вопросы» (задачу нельзя отметить выполненной, пока они не закрыты); у сводки ревью (`review.md` изменения) — упрощения, долг, зрелость; у ADR — варианты и драйверы |
| markdownlint и ссылки (lychee) | `make check`, внешние ссылки — CI | единое оформление Markdown; ссылки не ведут в никуда |
| Тесты хуков и скриптов процесса | `make check` | хук, который не даёт агенту менять тесты вне фазы их написания (TDD — сначала тест, потом код), и остальные проверки сами покрыты тестами |
| Коммиты: commitlint, gitleaks, правила репозитория | pre-commit, CI | формат сообщений, нет секретов, правки инструкций агента — отдельным коммитом, `Refs:` на требования, нет отладочных `DEBUG:` |
| Трейлер `Assisted-by` у коммитов агента | commit-msg | видно, какой коммит сделан с ИИ; коммиты человека проходят без трейлера |
| `/security-review` с DoS и rate limiting | по запросу, в сводке ревью | официальная команда Claude Code по умолчанию не ищет отказ в обслуживании; проектная копия ищет ([команда](.claude/commands/security-review.md)) |
