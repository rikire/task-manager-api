# Переработка README перед сдачей — рабочий документ

Что и почему меняем в README и документации перед сдачей задания (`CON-PLAN-deadline`, 2026-10-09):
решения владельца, план, результаты анализа. Документ рабочий: живёт в ветке `chore/readme-polish`, после
переработки его содержание переходит в README и коммиты, а сам он удаляется (правило «каждый артефакт
читается или удаляется», [01](pre-init/01-process-frame.md)).

## Цель

Репозиторий понятен и нагляден с первого экрана: проверяющий за несколько минут видит, как запустить, как
устроено решение и почему, как работал ИИ и как принимались решения, — не читая десятки md-файлов. Для
этого — диаграммы вместо абзацев и README как самодостаточная карта; остальные документы — по ссылке за
деталью.

## Кто читает и что проверяет

Источник — текст задания (`docs/task/assignment.txt`, строки 102–138, 155):

- пять обязательных разделов README в порядке задания; раздел про ИИ — «коротко», с конкретикой;
- проект поднимается строго по README;
- решения в коде совпадают с README — отдельный критерий оценки;
- «как вы рассуждаете» — неоднозначные места задания: выбрать вариант и описать в README;
- «как вы шли к решению» — история коммитов (не сжималась, слияние rebase);
- следующий этап — рассказ о решении и правка кода без ИИ: README — опора владельца на созвоне.

6. Формат ошибок описать честно: тело по RFC 9457, но `type` и `title` — значения Symfony по умолчанию

   [обзор архитектуры](architecture/README.md); запись `IMP` на исправление.
7. «Что дальше» — продуктовый долг из реестра (`IMP-012`, `IMP-014`) и формат ошибок.

10. Роадмап, строка 9 («плашки») — убрать противоречие «если успеем / сделано».
11. Сквозной пример одного изменения (`status-delete`) в разделе про ИИ — вместо части общих пунктов.
12. Раздел «Где задание можно понять по-разному и что выбрано» (`CON-DELIV-ambiguity-in-readme`): развилки

### Скелет README

```text
# Task Manager API — плашки, 2–3 строки «что это», маршрут для проверяющего
## Как запустить (+ попробовать API, эндпоинты)
## Архитектурные решения и компромиссы
   диаграммы: схема данных; модули и порт StatusUsage; удаление статуса
   карта кода
## Где задание можно понять по-разному и что выбрано
## Что дальше (добавил бы / сделал бы иначе)
## Использование ИИ — диаграмма процесса изменения (человек / агент, проверки), пример status-delete
## Сколько времени ушло — диаграмма хронологии, цифры
--- приложения ---
## Предыстория · ## Разработка · ## Проверки сверх базовых требований
```

Диаграммы — Mermaid: GitHub рисует их прямо в Markdown; в репозитории уже две
([обзор архитектуры](architecture/README.md)). Каждая диаграмма заменяет абзац, а не добавляется к нему.

### Факты для README (агент, 2026-10-08)

- **Объём.** Markdown в git — около 280 тысяч слов (`docs/pre-init/` — 57 файлов, `openspec/` — 38,
  `.claude/` — 35); PHP в `src/` и `tests/` — около 4 600 строк. Читатель без карты в этом тонет — отсюда
  цель «README как карта».
- **Схема данных** (миграции `Version20261007120000`, `…130000`): `status(id UUID, name VARCHAR(50),
  title VARCHAR(255))`, `task(id UUID, title VARCHAR(255), description TEXT NULL, created_at, updated_at,
  status_id)`, `fk_task_status … ON DELETE RESTRICT`.
- **Код:** `src/{Task,Status}/{Domain,Application/<сценарий>,Infrastructure/{Http/<сценарий>,Persistence}}`,
  `src/Shared/Infrastructure/Http`. Сценарии Task: Create, Get, List, ChangeTaskStatus, Delete; Status:
  Create, Get, List, Delete.
- **Хронология по коммитам** (время первого и последнего коммита, не длительность работы):
  `pre-init` — до 10-06 14:53 (вне git); harness и инициализация — 10-06 16:32 … 10-07 14:52
  (`architecture-kickoff` 10-07 09:24–11:32, `finish-init` 12:25–14:52); `status-catalog` 10-07 16:40–22:10;
  `task-crud` 22:39–23:17; `task-status-change` 23:48; `status-delete` 10-08 08:37; `json-unicode` 09:48.
  Для диаграммы честнее `timeline` по дням, чем `gantt` с выдуманными длительностями.
- **Неоднозначности задания (п. 12)** — уже разобраны в ADR-0007 как D1–D5 с вариантами: связь задачи со
  статусом, удаление используемого статуса, поля статуса, форма ответа, ссылки на несуществующее; плюс
  свободные переходы статусов (`REQ-TASK-status-change`).
- **Решения человека с причиной против рекомендации агента** — ADR-0006: владелец выбрал полную
  гексагональную структуру и два модуля вместо более лёгкой рекомендации агента; ADR-0001: версию Symfony
  владелец оставил на рекомендацию агента. Это готовые примеры для раздела про ИИ.

Главные замечания:

- **Голос.** README говорит об авторе в третьем лице («владелец принял эту цену», «владельцу стало
  интересно», «оценка владельца») — читается так, будто README писал кто-то другой. Для README кандидата —
  сильный сигнал генерации. Кандидат на решение владельца: писать от первого лица.
- **Первый экран:** 12 плашек и абзац о них, «два проекта в одном» с извинением за объём процесса, длинный

  «Реестр улучшений» ведёт в `debt.md` — неясно, один файл или два.
- **Таблица из 16 проверок** читается как сигнал оверинжиниринга; задание просит «кратко обосновать».
- **Непроверяемое:** «каждый коммит принят им» — что значит «принят»; UUID в верхнем регистре → 404 без
  причины; «решения 01–30 до открытия задания» — README сам признаёт, что в git не видно.
- **Фразы-наполнители:** строки 29, 130–131, 181–183, 265.

Пять правок по убыванию пользы (по мнению субагента): время на продукт и «что сделал бы иначе»; порядок

конкретика в разделе про ИИ, первое лицо, ID вне основного текста, таблица проверок — 5–6 строк.

### Внешние практики и скиллы (субагент `researcher`, 2026-10-08)

- **Чего ждут от README тестового задания** (вторичные источники — блоги и шаблоны оценки, не нанимающие
  инженеры): проект поднимается по README точными командами; допущения и компромиссы записаны, включая
  что не сделано и почему; архитектура по размеру задачи — оверинжиниринг штрафуют; красный флаг —
  README обещает, а код не работает или не совпадает. GitHub: README — что это, зачем, как начать;
  длинное — в другие документы ([docs.github.com](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)).
- **Mermaid на GitHub:** версия не опубликована (узнать — блок `info`); `flowchart`, `sequenceDiagram`,
  `erDiagram`, `stateDiagram-v2` — безопасны; C4 по сообщениям рисуется сырым текстом, `architecture-beta`
  не подтверждён, `timeline` и `gantt` не проверены — **проверить на GitHub до коммита**. Клики в
  диаграммах выключены (`securityLevel: strict`) — ссылки давать текстом рядом. Свои цвета (`classDef`,
  `style`) плохо читаются в тёмной теме — не задавать. Для доступности — `accTitle`/`accDescr` и строка
  текста рядом с диаграммой.
- **Другие средства без внешних сервисов:** alerts `> [!NOTE]` (не больше одного-двух на документ),
  свёрнутые `<details>`, автоматическое оглавление GitHub (кнопка Outline). Генератора ER-диаграммы из
  Doctrine в Mermaid нет — `erDiagram` пишем руками по миграциям.
- **Скиллы:** в репозитории уже есть `doc-coauthoring` (Anthropic) и свои `writing` + `reader-tester`;
  найденные community-скиллы для README и Mermaid (`shpigford/skills readme`, `make-readme`,
  `mermaid-diagrams`, `mermaid-cli`) почти ничего не добавляют к ручному проходу. Рекомендация — ничего не
  ставить.
