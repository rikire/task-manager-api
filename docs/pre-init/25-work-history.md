# 25. История работы

**Статус:** принято 2026-10-06, человек. **Область:** 2 «Планирование и трекинг».

## Потребность

История проекта должна читаться: по коммитам видно, что и зачем изменилось, как это связано с планом
и где работал ИИ. Нужно определить формат и размер коммитов и решить, нужны ли журнал работы с ИИ,
учёт времени и стоимости, хранение транскриптов сессий.

## Варианты

- **Формат коммитов:** свободный / Conventional Commits (`тип(область): тема`) с проверкой
  commitlint.
- **Журнал работы с ИИ:** нет / файл, который агент дописывает по хуку в конце сессии.
- **Время и стоимость:** скорость по git / ccusage (токены и стоимость по локальным логам Claude
  Code) / телеметрия OpenTelemetry.
- **Транскрипты сессий** (Claude Code автоматически хранит логи сессий локально, в
  `~/.claude/projects/`): не трогать / копировать в репозиторий.

## Решение

1. **Conventional Commits:** `тип(область): тема`.
   - тип — `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`;
   - область — имя изменения OpenSpec (`feat(add-to-cart): …`); для инструкций агента —
     `chore(agent): …`; для работы вне изменения (ветка `chore/<slug>`, [28](28-hosting-ci-git.md)) —
     `chore` или `refactor` без области изменения и без `Refs:`;
   - тело — зачем; правки человека, если были ([21](21-attribution.md));
   - трейлеры — `Refs:` ([09](09-traceability.md)) и `Assisted-by:` ([21](21-attribution.md)).

   commitlint проверяет формат в commit-msg хуке и в CI.
2. **Язык:** типы — английские (стандарт); тема и тело — по-русски: историю читает в основном
   человек ([23](23-documentation.md), язык по основному читателю).
3. **Размер:** коммит на группу задач `tasks.md` внутри ветки изменения, каждый зелёный, после приёмки
   ([05](05-tdd.md)) + отдельные коммиты инструкций ([21](21-attribution.md)); размер держат вертикальный срез и предупреждение о размере
   диффа ([18](18-human-comprehension.md)).
4. **Журнал работы с ИИ не ведём:** история уже есть в git, архиве изменений OpenSpec, ADR и журнале
   сбоев ([22](22-process-learning.md)); автожурнал по хуку на прошлом проекте автора дал сотни
   служебных коммитов и шум в истории.
5. **Время и стоимость:** только скорость по git ([24](24-planning-tracking.md)). ccusage и
   телеметрию не используем.
6. **Транскрипты сессий** в репозиторий не копируем: они остаются только в локальных логах Claude
   Code и могут содержать секреты.

## Обоснование

- Git — главный долговременный артефакт; conventional commits с commitlint — гарантия формата,
  атомарность — договорённость; журнал по хуку — запуск гарантирован, содержание пишет модель;
  OTel окупается при нескольких людях или проектах; в транскриптах могут быть секреты
  ([ч.7 §8](research/report/07-guardrails-harness-process.md)).
- Отказ от журнала, ccusage и телеметрии — решения человека (пятый принцип,
  [01](01-process-frame.md)).

## Гарантия

- Формат коммитов — **Гф** (commitlint в хуке и CI).
- Язык, содержание тела — **Д**.
- Скорость по git — вычисляется скриптом (**Гф**).
