# 23. Документация

**Статус:** принято 2026-10-06, человек. Структура и пути — предварительные, сверяются в вопросе №31
«Финальная сверка» [очереди](to-be-discussed.md). **Область:** 4 «Контекст и инструкции».

## Потребность

После инициализации в проекте появится много документов: инструкции агенту, спеки, архитектура, ADR,
реестры, описание процесса. Нужно определить, какие документы есть, где лежат, кто их читает, какие
нормативные, что генерируется, на каком языке пишется — и как держать всё это целостным, чтобы и
человек, и агент сразу понимали, куда смотреть.

## Варианты

- **Навигация:** обзор в AGENTS.md / отдельный реестр документов.
- **Живое описание процесса:** восемь файлов по областям / один файл.
- **Изменения процесса после заморозки `docs/pre-init/`:** новый тип документа / ADR.
- **Целостность:** договорённость / исполняемые проверки в CI (ссылки, генерация, контракт API).
- **Язык:** всё на английском / агенту английский, человеку русский.

## Решение

### 1. Структура

```
AGENTS.md                  для агента · нормативный · карта «ситуация → механизм» ведёт в docs/README.md
CLAUDE.md                  @AGENTS.md + только для Claude Code
README.md                  для человека · что это, как запустить, куда смотреть дальше
docs/
  README.md                реестр документов + реестр префиксов ID + навигация (точка входа)
  roadmap.md               цель, скоуп, вне рамок, изменения, вехи (24)
  glossary.md              термины домена и процесса (роадмап, 34)
  process/                 как работаем сейчас: файл на каждую из 8 областей (01; роадмап, 34)
  api/curl-examples.md     примеры запросов к API (33)
  architecture/README.md   урезанный arc42 (11)
  adr/                     ADR + генерируемый индекс README.md (12)
  registers/
    debt.md                DEBT и IMP (10), заводится при первой записи
    failures.md            FAIL (22), заводится при первом сбое
    traceability.md        матрица трассировки, генерируется (09; роадмап, 34)
  pre-init/                заморожено
openspec/                  спеки и изменения (02)
<контракт API>             путь и формат — по стеку, ADR на старте архитектуры
```

### 2. Реестр документов `docs/README.md`

Таблица по каждому документу: путь; для кого (человек / агент / оба); нормативный или описательный
(отсюда проверки берут список нормативных мест — [08](08-normative-descriptive.md)); генерируется или
вручную; кто ведёт. Там же — реестр префиксов ID (`R-`, `Q-`, `C-` с допустимыми областями, `ADR-`,
`DEBT-`, `IMP-`, `FAIL-`, реестр алиасов переименований — [09](09-traceability.md)) и ссылка на
глоссарий. Карта в AGENTS.md ([03](03-agent-instructions.md)) ведёт сюда.

### 3. Живое описание процесса — `docs/process/`

Восемь файлов, по одному на область из [01](01-process-frame.md), по её шаблону: процессы, правила
(с классом гарантии и `Source:` на документ решения, ADR или запись журнала сбоев `FAIL-…`), артефакты, проверки.

### 4. Изменения процесса после заморозки

Оформляются как ADR с пометкой `process` — тот же механизм: варианты, компромиссы, принятие коммитом
([12](12-adr.md)). Пример: «добавлен хук на правку миграций после FAIL-004».

### 5. Контракт API

Обязателен; CI проверяет его соответствие коду. Формат и подход (контракт из кода или код из
контракта) — архитектурное решение по стеку, ADR на старте архитектуры
([11](11-architecture-design.md)).

### 6. Язык

Язык — по основному читателю:

| Английский (читает в первую очередь агент) | Русский (читает в первую очередь человек) |
|---|---|
| AGENTS.md, CLAUDE.md, `.claude/rules/`, скиллы, сообщения хуков | README.md, `docs/README.md`, `docs/glossary.md` (с английскими терминами в скобках) |
| спеки и изменения OpenSpec (`--language` — английский) | `docs/process/`, `docs/architecture/README.md` |
| ADR | `docs/registers/` |

Комментарии в коде — [30](30-code-comments.md). Заглавные ключевые слова MUST / SHALL ([08](08-normative-descriptive.md))
применяются в английских нормативных документах; в русских нормативных документах правило — пункт
раздела «Правила» с `Source:`.

### 7. Объём и стиль

Жёстких лимитов нет ([03](03-agent-instructions.md)); правила письма и проверка читателем —
[19](19-agent-writing.md). Каждый документ начинается со строки «что это и для кого».

### 8. Проверки целостности в CI

- markdown-ссылки (`lychee`) и существование упомянутых путей, скиллов, команд
  ([03](03-agent-instructions.md));
- `Source:` и заглавные ключевые слова вне нормативных мест ([08](08-normative-descriptive.md));
- формат и существование ID ([09](09-traceability.md));
- свежесть генерируемых файлов — матрица, индекс ADR ([09](09-traceability.md), [12](12-adr.md));
- markdownlint ([19](19-agent-writing.md));
- **каждый файл в `docs/` есть в реестре `docs/README.md`.**

## Обоснование

- Целостность гарантируют только исполняемые проверки; для backend самая сильная — контракт API,
  проверяемый против кода; выводимое из кода не документируется, руками пишутся «почему» и
  подводные камни ([ч.6 «Документация»](research/report/06-context-security-docs.md),
  [ч.3 п.9](research/report/03-weaknesses.md)).
- Обзоры репозитория агенту не помогают, а индекс «что есть и когда использовать» помогает
  ([03](03-agent-instructions.md)) — отсюда реестр документов как точка навигации.
- Восемь файлов процесса и русский язык для документов человека — решения человека (читает
  по-русски быстрее).

## Гарантия

- Проверки из §8 — **Гф**; контракт API против кода — **Г** в пределах проверки.
- Структура, язык, «что это и для кого» — **Д**; проверка читателем — **В**.

## Где будет реализовано

- Файлы и папки из §1 создаются по порядку из [34](34-core-vs-roadmap.md); реестры — при первой записи;
  пока нет `docs/process/`, процесс описывают `docs/pre-init/` и AGENTS.md.
- Папка git-хуков — `.githooks/` ([29](29-environment.md)); реестр алиасов ID — раздел `docs/README.md`.
- Скрипты проверок из §8 — в pre-commit и CI.
- `openspec/config.yaml` — `--language` английский.
