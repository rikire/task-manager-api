# 29. Окружение и воспроизводимость

**Статус:** принято 2026-10-06, человек. **Область:** 5 «Ограничения».

## Потребность

Проект и весь процесс разработки должны подниматься на чистой машине минимальным числом действий,
с одинаковыми версиями инструментов у всех, и с реально работающими хуками и ограждениями. Нужно
также, чтобы главный README сразу объяснял, что происходит в репозитории и как его запустить.

## Варианты

- **Версии инструментов:** вручную по документу / менеджер версий mise (`mise.toml` + `mise.lock` с
  контрольными суммами) / всё в Docker, включая отдельный контейнер с инструментами / devcontainer /
  Nix.
- **Точка входа для подготовки и команд:** Makefile (`make setup`) / задачи mise (`mise run setup`) /
  скрипт / `composer run-script`.
- **Проверка воспроизводимости:** документ «как начать» (договорённость) / CI-джоб «чистый клон»
  (гарантия).

## Решение

### 1. Два пути

- **Путь проверяющего:** `git clone` → `docker compose up -d` → API работает. Нужен только Docker:
  приложение и его зависимости живут в контейнерах. Требование задачи — [31](31-task-requirements.md).
- **Путь разработки** (человек и агент): плюс инструменты процесса.

### 2. Версии инструментов процесса — mise на хосте

- mise (`jdx/mise`, MIT) закрепляет в `mise.toml` / `mise.lock` версии Node, OpenSpec
  ([02](02-sdd-framework.md)), линтеров markdown и коммитов, проверки ссылок, jscpd, gitleaks ([32](32-stack-tools.md)); задаёт переменные
  окружения проекта (`OPENSPEC_TELEMETRY=0`). Ставится с одобрения человека при инициализации.
- Отдельного Docker-контейнера для инструментов нет — лишняя задержка для хуков.
- Инструменты языка приложения (статанализ, линтер, тесты) — рекомендация: запускать в уже
  работающем контейнере приложения (`docker compose exec`), а не ставить рантайм на хост;
  окончательно — [32](32-stack-tools.md).

### 3. Точка входа — Makefile

`make` — единая точка входа для всех команд: `make setup`, `make up`, `make test`, `make check` и
т.д.; эти же команды — в AGENTS.md ([03](03-agent-instructions.md)).

`make setup` (повторный запуск безопасен):
- ставит инструменты по `mise.lock`, включая закреплённый OpenSpec;
- включает git-хуки (`core.hooksPath` → папка с хуками в репозитории; [04](04-definition-of-done.md),
  [21](21-attribution.md), [25](25-work-history.md));
- ставит плагины проекта (`claude plugin install … --scope project`, [20](20-skills.md));
- пишет в локальные настройки маскировку секретов `sandbox.credentials` ([15](15-agent-security.md));
- проверяет наличие bubblewrap, git, gh, Claude Code и подсказывает, что поставить;
- в конце запускает проверку здоровья ([16](16-guardrails-harness.md)), и печатает чек-лист следующих шагов, включая
  подтверждение доверия к папке.

mise не ставится через `curl | sh`: так в цепочку попадает непроверенный скрипт; он — предустановка
из README.

### 4. Доверие к рабочей папке

При первом запуске `claude` в репозитории нужно подтвердить доверие (workspace trust): без него
Claude Code не применяет разрешения из `.claude/settings.json` и хуки субагентов. Это шаг онбординга;
проверка здоровья на SessionStart предупреждает, если доверие не принято.

### 5. Контрольные суммы

Через lock-файлы (`mise.lock`, lock-файл менеджера пакетов стека). Скачиваемое мимо менеджеров —
с суммой, зафиксированной в репозитории заранее, и сверкой.

### 6. CI-джоб «чистый клон»

`git clone` → команды «Быстрого старта» README (`docker compose up -d`, проверка API —
[33](33-readme.md)) → `make setup` → проверка, что git-хуки стоят (коммит с заведомо плохим файлом
должен упасть) → полный набор проверок ([28](28-hosting-ci-git.md)). В CI нет Claude Code и
bubblewrap: `make setup` пропускает связанные с ними шаги.

### 7. Главный README (предварительно)

Заменено решением [33](33-readme.md); ниже — исходная предварительная структура. На русском ([23](23-documentation.md)). Разделы:
1. **Что это** — 1–2 предложения.
2. **Быстрый старт** (путь проверяющего): нужен Docker; команды; адрес API и чем проверить; примеры
   curl.
3. **Архитектурные решения и компромиссы** — 3–7 пунктов со ссылками на ADR.
4. **Как устроен репозиторий** — карта со ссылками: `docs/README.md`, роадмап, архитектура, ADR,
   спеки OpenSpec, процесс, pre-init.
5. **Как ведётся разработка** — процесс в пять строк (изменение OpenSpec → тесты → реализация →
   проверки → приёмка и PR), ссылка на `docs/process/`.
6. **Разработка: подготовка машины** — предустановки (git, Claude Code, gh, mise, make, bubblewrap),
   `make setup`, первый запуск `claude` с подтверждением доверия, таблица команд `make`.
7. **Использование ИИ** — как работает агент, как проверялся результат, трейлер `Assisted-by`.
8. **Что дальше** — сводка из роадмапа и реестра улучшений и долга.
9. **Сколько времени ушло** — честная цифра.

Разделы 3, 7, 8, 9 и примеры curl требует задача ([31](31-task-requirements.md)); остальное от задачи не зависит.

## Обоснование

- Гарантию воспроизводимости дают lock-файлы с контрольными суммами и проверка на чистой машине в CI;
  документ онбординга — договорённость; `mise.lock` проверяет скачанные артефакты по суммам; без
  workspace trust не применяются разрешения проекта и хуки субагентов; для малого проекта достаточно
  lock-файла, `mise.lock`, одной команды подготовки и джоба «чистый клон»
  ([ч.7 §3](research/report/07-guardrails-harness-process.md)).
- mise на хосте вместо контейнера с инструментами, Makefile, структура README с учётом требований
  задачи — решения человека.

## Гарантия

- `mise.lock` и lock-файлы — **Г** (версии и суммы).
- Джоб «чистый клон» — **Г**: подготовка работает, хуки ставятся.
- `make setup` и шаг доверия — **Д** (их надо выполнить); проверка здоровья делает пропуск заметным.
