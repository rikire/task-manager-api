# 01. Каркас процесса

**Статус:** принято 2026-10-05, человек. Пробное: пересматривается, если по ходу оказывается неудобным.

## Потребность

Нужно решить, на какие области делится процесс разработки с ИИ-агентом и как описывается каждая
область. Классические модели (CMMI, PMBOK) рассчитаны на команду людей; с агентом узкие места другие —
проверка результата, формулировка намерения, контекст агента и понимание кода человеком. От каркаса
зависит, куда ложатся остальные решения и как устроена документация процесса.

## Варианты

Из исследования ([report.md](research/report.md), раздел «Итог, а)»):

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| A. DORA AI Capabilities | 7 организационных условий успеха ИИ в разработке (Google DORA, 2025) | самая широкая эмпирика | командный уровень; нет слабостей агента, проверки, понимания кода |
| B. Guides / sensors (Böckeler, Thoughtworks) | механизмы делятся на направляющие (до действия) и сенсоры (после), каждый — вычислительный или на LLM | прямо разделяет гарантию и договорённость | нет требований, планирования, понимания кода |
| C. Жизненный цикл / SDD | фазы: намерение → спека → дизайн → задачи → реализация | сильные требования и планирование | спека — тоже договорённость; много текста для чтения |
| D. Вокруг узких мест | области: намерение, контекст, ограничения, проверка, обучение, понимание | единственный с пониманием кода как областью | слабые требования, планирование, архитектура |
| **D + B + лёгкий C** | области из D, классификация механизмов из B, требования и планирование из C | закрывает слабые места каждого | синтез, как целое не проверялся |

**Лёгкий C** — из жизненного цикла берутся только спека в виде дельты и план задач внутри изменения
([02](02-sdd-framework.md)), без обязательных отдельных фаз.

## Решение

Выбран **D + B + лёгкий C**.

### Области

| # | Область | Какой сбой предотвращает |
|---|---|---|
| 1 | Намерение и требования | агент строит не то, додумывает, выдумывает ограничения |
| 2 | Планирование и трекинг | расползание скоупа, потеря нити между сессиями, незаписанный долг |
| 3 | Архитектура и решения | дрейф архитектуры, несогласованные решения, свой велосипед |
| 4 | Контекст и инструкции | агент не знает правил или получает их не в тот момент; раздутые документы |
| 5 | Ограничения | необратимые действия, обход проверок, секреты, инъекции |
| 6 | Проверка | ложное «готово», плохие тесты, уязвимости, тяп-ляп |
| 7 | Понимание и авторство | человек не знает и не может объяснить код |
| 8 | Обучение процесса | повтор той же ошибки; правило, которое ничего не меняет |

Области 2 и 3 добавлены к D, область 1 расширена требованиями из C: в варианте D это слабые места.
Артефакты продукта (спеки, ADR, контракт API) отдельной плоскостью не выделяются: это артефакты
областей 1 и 3.

### Классы механизмов

| Класс | Значение |
|---|---|
| **Г** | гарантия: исполняется вне модели (хук, права, песочница, CI) |
| **Г запуска** | гарантировано, что проверка выполнится, но не что она поймает всё |
| **Г доставки** | гарантировано, что текст попадёт в контекст агента, но не что агент его выполнит |
| **Гф** | гарантия формы: машина проверяет наличие и структуру, не смысл |
| **В** | вероятностная проверка: проверяет LLM, вердикт может ошибаться |
| **Д** | договорённость: агент или человек может не выполнить |
| **Ч** | суждение человека |

Запрос подтверждения (`ask`) — «промпт **Г**, решение **Ч**».

### Шаблон описания области

```
# <Область>
Сбой, который предотвращает: ...

Процессы:   когда запускается · шаги · кто (человек / агент / автоматически)
Правила:    правило · класс · Source: документ решения, ADR или ID требования
Артефакты:  где лежит · кто читает (человек / агент) · генерируется или вручную
Проверки:   что проверяется машиной и где (хук / CI)
```

### Сквозные принципы

1. **Лестница.** Для каждого правила берётся самый высокий уровень, который можно выразить кодом:
   тест → проверка в CI → хук → запрет в правах (`deny`) → eval (прогон агента на наборе задач с
   правилом и без) → строка в инструкции. Порядок — от того, что труднее обойти и что срабатывает
   раньше, к тому, что держится только на послушании агента.
2. **Гейт без защиты от обхода не считается гарантией.** Каждая гарантия проверяется на обход, и
   проверяет её не агент, который её написал: субагент в свежем контексте или человек (механизм —
   [16](16-guardrails-harness.md)).
3. **Машина проверяет форму, человек — смысл.** Смысл машиной не гарантируется, это признаётся явно.
4. **Каждый артефакт для чтения должен окупаться.** Если человек его не читает, артефакт удаляется.
5. **Механизм вводится под сбой** — наблюдаемый или доказанный исследованием, а не «на всякий случай».
   Бюджет на процесс задаётся порядком внедрения и контрольной точкой ([34](34-core-vs-roadmap.md)), а
   не числом.

## Обоснование

- Устоявшейся таксономии областей нет; каркас под соло-разработчика собирается из нескольких рамок
  ([ч.1 §1.2](research/report/01-landscape-sdd.md)).
- Шесть кластеров «вокруг узких мест» — синтез отчёта ([ч.1](research/report/01-landscape-sdd.md),
  «Как сравнивать»).
- Три кластера слабостей агента требуют разных механизмов: внешние проверки, гейты с защитой от
  обхода, запись допущений в артефакты, которые читает человек
  ([ч.3 «Общий корень»](research/report/03-weaknesses.md)).
- Лестница и правило «хук гарантирует запуск, а не исправление» —
  [ч.7](research/report/07-guardrails-harness-process.md), [ч.3](research/report/03-weaknesses.md).
- Инструкции сдвигают частоту ошибок, но не убирают их; вендор называет CLAUDE.md «context, not
  enforced configuration» ([report.md](research/report.md), вывод 8).
