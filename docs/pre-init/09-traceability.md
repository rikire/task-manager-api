# 09. Трассируемость

**Статус:** принято 2026-10-05, человек; изменено 2026-10-05: ID со слагами (`R-CART-add-to-cart`)
вместо номеров (`R-CART-001`) — номер ничего не говорит читателю. **Область:** 1 «Намерение и
требования».

## Потребность

Нужно связать требование, тест, код и коммит: понимать, зачем существует каждый кусок кода, видеть
непокрытые требования и поведение, которого никто не просил.

## Варианты

- ID требований в спеке.
- ID в имени или метке теста + CI-проверка покрытия.
- Трейлер (служебная строка в конце сообщения коммита) + проверка.
- Связь кода с требованием через комментарии.
- Обратная проверка: тест без требования.
- Матрица трассировки: вручную / агентом на ходу / генерируется скриптом.
- Инструменты управления требованиями (StrictDoc, Doorstop, sphinx-needs) — избыточны для малого
  проекта.

## Решение

### 1. Типизированные ID со слагами

| Сущность | Формат | Пример |
|---|---|---|
| Требование | `R-<CAP>-<slug>` | `R-CART-add-to-cart` |
| Сценарий требования | `R-<CAP>-<slug>.<slug-сценария>` | `R-CART-add-to-cart.out-of-stock` |
| Сценарий качества ([11](11-architecture-design.md)) | `Q-<ATTR>-<slug>` | `Q-PERF-cart-p95` |
| Ограничение (правило в AGENTS.md, `.claude/rules/`) | `C-<AREA>-<slug>` | `C-TEST-no-mocking-sut` |
| ADR | `ADR-NNNN-<slug>` (так же назван файл) | `ADR-0004-error-format` |
| Долг | `DEBT-NNN-<slug>` | `DEBT-012-no-retry-on-timeout` |
| Улучшение | `IMP-NNN-<slug>` | `IMP-007-batch-import` |
| Сбой агента ([22](22-process-learning.md)) | `FAIL-NNN-<slug>` | `FAIL-003-edited-tests-to-pass` |

- `<CAP>` — capability OpenSpec (папка в `openspec/specs/`), заглавными; `<ATTR>` — атрибут качества
  (`PERF`, `SEC`, `REL`…); `<AREA>` — область правила (`TEST`, `ARCH`, `SEC`…). Допустимые значения —
  в реестре префиксов ([23](23-documentation.md)).
- **Слаг:** kebab-case, латиница, 2–4 слова; для требований — глагол + объект.
- **Номер** — только у журналов (ADR, DEBT, IMP, FAIL), где важен порядок. У ADR четыре цифры (привычный
  формат ADR), у DEBT, IMP и FAIL — три. Номера не переиспользуются.
- **ID неизменен после создания.** Заголовок можно переписывать, ID — нет; при изменении требования
  (`MODIFIED` в дельте OpenSpec) ID сохраняется; удалённый ID не переиспользуется. Если слаг стал
  вводить в заблуждение, переименование — только скриптом, который заменяет ID по всему репозиторию и
  добавляет запись «старый → новый» в реестр алиасов: старые трейлеры в истории git не меняются и
  должны находиться. Скрипт пишется, когда переименование впервые понадобится.
- **CI проверяет:** формат, уникальность слага внутри capability или журнала, что удалённый ID не
  переиспользован.

Как ID выглядит в спеке:

```markdown
### Requirement: R-CART-add-to-cart — добавление товара в корзину
The system SHALL ...

#### Scenario: R-CART-add-to-cart.out-of-stock
- WHEN ...
- THEN ...
```

### 2. Тесты → сценарии

- Точный ID сценария ставится в метку или аннотацию теста; имя тестовой функции — читаемое, в стиле
  языка (`test_add_to_cart_out_of_stock`), потому что дефис в имени функции часто недопустим.
  Трассировка идёт по метке.
- **Требование покрыто, если покрыт каждый его сценарий.** CI проверяет, что у каждого сценария есть
  тест.

### 3. Тесты без требования

Помечаются меткой `internal` с объяснением, **зачем существует компонент** — его назначение и
ответственность, без перечня мест использования (такой перечень устаревает; места использования
находятся поиском). Если назначение внятно не объясняется — сигнал, что компонент лишний.

### 4. Код → требование

Комментарий с ID в точках входа поведения (обработчик, use case), не на каждой строке. CI проверяет,
что каждый упомянутый в коде ID существует. Правила комментариев — [30](30-code-comments.md).

### 5. Коммиты

Трейлер `Refs: R-CART-add-to-cart, R-CART-remove-from-cart` обязателен в коммитах, которые меняют код
вне тестов и документации (список путей — по стеку). Проверка — в commit-msg хуке и CI. Набор
трейлеров согласован с атрибуцией ИИ: `Assisted-by` ([21](21-attribution.md)).

### 6. Матрица трассировки

- **Генерируется скриптом** из фактов: ID в спеках, метки в тестах, результаты прогона тестов,
  трейлеры. «Покрыт» = тест с ID сценария существует и проходит.
- Pre-commit перегенерирует файл матрицы по результатам тестов, которые он и так запускает
  ([04](04-definition-of-done.md)), и добавляет файл в коммит; CI падает, если закоммиченная матрица
  устарела. Нестабильный («флейки») тест — это дефект, который чинится, а не повод отключить проверку.
- Агенту запрещено править файл матрицы своими инструментами (`deny`); git-хук правит его штатно.
- «Покрыт» ≠ «выполнено по смыслу»: смысл проверяет человек при приёмке
  ([04](04-definition-of-done.md)).

### 7. Правила и ADR

Трассируются через `Source:` ([08](08-normative-descriptive.md)).

## Обоснование

- Лёгкая схема (ID → тест + CI → трейлер) стоит часы и окупается на малом проекте; инструменты
  управления требованиями — для регулируемых доменов и сотен требований
  ([ч.4 §5](research/report/04-requirements-planning.md)).
- Обратная проверка ловит поведение, которого никто не просил; проверки покрытия силами LLM (Spec Kit
  `/analyze`) — договорённость, скрипт даёт гарантию формы
  ([ч.4 §5](research/report/04-requirements-planning.md)).
- Данных, что трассировка улучшает результат в агентной разработке, нет; довод — человек понимает,
  зачем существует каждый кусок кода ([ч.4 §5](research/report/04-requirements-planning.md)).
- Агент выдаёт неверное измерение за факт и отмечает непроверенное как выполненное — поэтому матрицу
  считает скрипт, а не агент ([ч.3 п.2, п.17](research/report/03-weaknesses.md)).

## Гарантия

Пока скрипты трассировки в роадмапе ([34](34-core-vs-roadmap.md)), commit-msg проверяет `Refs:` только
синтаксически, а покрытие сценариев и существование ID — договорённость.


- Покрытие сценариев, существование ID в коде, наличие трейлера, свежесть матрицы — **Гф**
  (pre-commit, CI).
- Запрет правки матрицы агентом — **Г** для встроенных инструментов (`deny`); git-хук пишет файл
  штатно, поэтому песочницей файл не закрывается.
- Объяснение у `internal`-тестов — **Гф** (наличие); смысл — **Ч**.
- Соответствие теста смыслу сценария — **Ч**.

## Где будет реализовано

- `openspec/config.yaml` → `rules.specs`: ID требований и сценариев.
- Скрипт трассировки (покрытие, существование ID, матрица) — в pre-commit и CI.
- Commit-msg хук для `Refs:`.
- Файл матрицы — путь по [23](23-documentation.md); `deny` на правку — [13](13-authority.md).
- Реестр префиксов ID и алиасов — по [23](23-documentation.md).
