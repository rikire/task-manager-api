# 14. Безопасность и надёжность кода

**Статус:** принято 2026-10-05, человек. **Область:** 6 «Проверка».

## Потребность

Агент допускает инъекции, N+1 (лишний запрос к БД на каждый элемент списка), слабую обработку ошибок
и другие уязвимости; безопасность сгенерированного кода не растёт вместе с моделями. Для бэкенда это
главный жёсткий риск. Нужно ловить типовые уязвимости автоматически и не изобретать защиту каждый раз
заново.

## Варианты

- SAST (статический анализ кода на уязвимости: Semgrep, CodeQL, Sonar) — гарантия запуска, полнота
  ограничена правилами.
- Детектор N+1 в режиме «падать» и проверки числа запросов в тестах — гарантия в пределах покрытия.
- Линтер обработки ошибок, сканер секретов, аудит зависимостей — гарантия.
- LLM-ревью безопасности (`/security-review` в Claude Code, GitHub Action) — находит больше, особенно
  логические уязвимости, но с большим числом ложных срабатываний; Action уязвим к prompt injection.
- OWASP ASVS (стандарт проверки безопасности приложений) как источник требований.
- DAST (сканирование запущенного приложения внешними запросами), фаззинг (подача случайного ввода).

## Решение

### 1. Детерминированный слой

| Когда ([04](04-definition-of-done.md)) | Проверка |
|---|---|
| pre-commit | сканер секретов; линтер обработки ошибок (проглатывание, голый catch, catch с возвратом значения по умолчанию) |
| в тестах (входят в pre-commit и CI) | детектор N+1 в режиме «падать» во всех интеграционных тестах; проверки числа запросов на ключевых эндпоинтах; тесты сбойных путей из сценариев нежелательного поведения ([07](07-requirements-intent.md)) |
| CI (push / PR) | SAST; аудит зависимостей; сканер секретов (повторно, так как pre-commit обходится) |

Конкретные инструменты — [32](32-stack-tools.md).

### 2. LLM-ревью безопасности

Вероятностное: находит больше, чем SAST, но часто ошибается, поэтому не блокирует.
- Агент предлагает `/security-review` в сводке для ревью, если изменение затрагивает авторизацию,
  разбор ввода, доступ к данным или секреты.
- В CI пока не запускается — только локально ([28](28-hosting-ci-git.md)). Если будет добавлен в CI —
  неблокирующим отчётом и только для собственных (доверенных) PR: на чужом PR ревьюер может
  выполнить внедрённую в код инструкцию.
- В конфигурацию `/security-review` добавляются DoS и rate limiting (по умолчанию он их не
  проверяет), если они важны для проекта.

### 3. Требования безопасности

На старте архитектуры (процесс А «Старт архитектуры», [11](11-architecture-design.md)) из OWASP ASVS
уровня 1 выбирается только относящееся к проекту → требования (`REQ-…`) или ограничения
(`RUL-SEC-<slug>`); форматы ID — [09](09-traceability.md). Каждое проверяется тестом или ревью.

### 4. Сквозная концепция «безопасность»

В `docs/architecture/README.md`: валидация ввода на границе; параметризованные запросы, без
склейки SQL из строк; проверка доступа к чужим ресурсам; ошибки не раскрывают внутренности; в логах
нет секретов и персональных данных.

### 5. Пока не берём

DAST и фаззинг — добавляются, если базовый слой пропустит реальный сбой (пятый принцип,
[01](01-process-frame.md)). Если контракт API будет в OpenAPI, фаззинг по схеме — недорогой
следующий шаг.

## Обоснование

- Уязвимости класса OWASP Top 10 в 45% случаев, крупные модели не лучше (Veracode, вендор); около
  половины корректных бэкендов эксплуатируемы (бенчмарк BaxBench)
  ([ч.5 «Безопасность и надёжность кода»](research/report/05-architecture-testing-verification.md),
  [ч.3 п.5](research/report/03-weaknesses.md)).
- SAST F1 0,26–0,55, LLM F1 около 0,75–0,80 с большим числом ложных срабатываний; совет авторов —
  LLM для широкой сортировки, сканеры для надёжной проверки
  ([ч.5](research/report/05-architecture-testing-verification.md)).
- `/security-review` по умолчанию исключает DoS и rate limiting; Action — только для доверенных PR
  ([ч.5](research/report/05-architecture-testing-verification.md)).
- Детекторы N+1 в режиме «падать» делают тесты красными при лишних запросах
  ([ч.5](research/report/05-architecture-testing-verification.md)).
- Глотание ошибок и подстановка значений по умолчанию — слабость, подтверждённая практикой
  ([ч.3 п.6](research/report/03-weaknesses.md)).

## Гарантия

- Сканер секретов, линтер ошибок, SAST, аудит зависимостей — **Г запуска** (полнота — в пределах
  правил).
- Детектор N+1, проверки числа запросов, тесты сбойных путей — **Г** в пределах покрытия тестами.
- LLM-ревью безопасности — **В**.
- Выборка из ASVS, сквозная концепция — **Д**, проверяются тестами и ревью.

## Где будет реализовано

- Pre-commit: сканер секретов, линтер ошибок; CI: SAST, аудит зависимостей.
- Конфигурация тестов: детектор N+1 в режиме «падать».
- `docs/architecture/README.md` — сквозная концепция «безопасность»; требования из ASVS — в спеках и
  правилах `RUL-SEC-*`.
- Настройка `/security-review` — локально; CI — [28](28-hosting-ci-git.md).
