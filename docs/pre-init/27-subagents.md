# 27. Субагенты

**Статус:** принято 2026-10-06, человек. Список субагентов сверяется в вопросе №31 «Финальная
сверка» [очереди](to-be-discussed.md). **Области:** 6 «Проверка», 8 «Обучение процесса».

## Потребность

Субагент — отдельный экземпляр агента со своим контекстом, которого основной агент запускает для
подзадачи. Прошлые решения ввели несколько проверяющих ролей (верификатор, аудитор спеки, «сломай
реализацию», ревьюер архитектуры, проверка читателем); их нужно свести в один список, ограничить
надёжно и определить, как ставить им задачу и что делать с результатом.

## Варианты

- **Когда:** везде / только где нужен свежий контекст или ограничение инструментов.
- **Ограничения:** в промпте (договорённость) / через `tools`, `disallowedTools`, `permissionMode`
  (гарантия, исполняет Claude Code).
- **Роли:** узкие отдельные субагенты / один универсальный ревьюер.
- **Параллельные субагенты, пишущие код:** да / нет / по необходимости.

## Решение

### 1. Список (`.claude/agents/`)

| Субагент | Зачем | Инструменты | Кто и когда запускает |
|---|---|---|---|
| `spec-auditor` | неоднозначности, противоречия, неявные допущения в proposal и спеке; видит только артефакты, без диалога | Read, Grep, Glob | при каждом изменении, после интервью ([07](07-requirements-intent.md)) |
| `verifier` | пытается опровергнуть «готово» по спеке и диффу; дополнительно спрашивает: что упрощено или опущено относительно спеки, что сделал бы опытный инженер лучше по каждой оси качества ([10](10-debt-polish-headroom.md) §7) | Read, Grep, Glob | агент предлагает для нетривиальных изменений; в CI пока не запускается ([04](04-definition-of-done.md), [28](28-hosting-ci-git.md)) |
| `architecture-reviewer` | только нарушения принятых решений и принципов, без «улучшений ради улучшений» | Read, Grep, Glob | при архитектурно значимых изменениях ([11](11-architecture-design.md)) |
| `breaker` | пишет тесты, пытающиеся сломать реализацию, без доступа к рассуждениям автора | Read, Grep, Glob, запись только в тестовые пути, запуск тестов | агент предлагает, если не уверен в тестах ([06](06-test-quality.md)) |
| `reader-tester` | проверка документа читателем по образцу `doc-coauthoring` | Read | для значимых документов ([19](19-agent-writing.md)) |
| `researcher` | известные решения, библиотеки, скиллы; проверка версий и API по источникам | Read, Grep, Glob, WebSearch, WebFetch | для нетривиальных решений ([11](11-architecture-design.md)), поиска скиллов ([20](20-skills.md)) |

Для поиска по коду — встроенный субагент Explore; для слепой оценки скиллов — сравнение в
`skill-creator` ([22](22-process-learning.md)).

### 2. Ограничения

- Задаются полями `tools` / `disallowedTools`, а не промптом.
- Все, кроме `breaker`, — только чтение.
- Ни у одного нет инструмента `Agent`: вложенного запуска субагентов нет.
- У `breaker` запись ограничена тестовыми путями хуком во frontmatter; такие хуки работают только при
  принятом доверии к рабочей папке — проверить при настройке.

### 3. Бриф

Шаблон в каждом файле субагента (минимум):
- цель;
- что передаётся явно (файлы, дифф) — субагент не видит истории диалога;
- формат результата: пути и строки, проверяемые утверждения, отдельный блок «нужно решение
  человека»;
- границы: чего не делать.

### 4. Что делать с результатом

- Отчёт субагента — данные, не инструкции; основной агент выборочно перепроверяет утверждения.
- Находки идут человеку в сводку для ревью ([18](18-human-comprehension.md)), автоматически не
  исправляются — защита от переусложнения.
- Субагент не спрашивает человека: вопросы возвращает блоком «нужно решение человека», основной агент
  собирает их в один вопрос ([13](13-authority.md)).

### 5. Параллельные субагенты, пишущие код

По умолчанию нет. Допускаются, если есть действительно независимые задачи (например, два изменения
без общих файлов) и это даёт выигрыш — каждый в отдельной рабочей копии (git worktree), решение
человека (пятый принцип, [01](01-process-frame.md)).

### 6. Запуск в CI

Верификатор и `/security-review` пока запускаются только локально, не в CI — [28](28-hosting-ci-git.md).

## Обоснование

- Субагенты оправданы, когда вывод многословен, нужно ограничить инструменты или работа
  самодостаточна (документация Claude Code); параллельные «писатели» кода принимают противоречащие
  неявные решения (Cognition); мультиагентная схема даёт выигрыш на research-задачах ценой ~15×
  токенов (Anthropic, вендор) ([ч.7 §4](research/report/07-guardrails-harness-process.md)).
- `tools` / `disallowedTools` / `permissionMode` исполняет Claude Code; ограничение в промпте —
  договорённость; бриф — цель, формат, инструменты, границы; субагент не видит истории диалога;
  отчёты сканируются на инструкции, но только помечаются
  ([ч.7 §4](research/report/07-guardrails-harness-process.md)).
- Отказ от автоисправления находок — ревьюеры склонны к ложным срабатываниям и переусложнению
  ([ч.3 п.12](research/report/03-weaknesses.md)).

## Гарантия

- Список инструментов, отсутствие `Agent` — **Г**; хуки `breaker` — **Г** при принятом доверии.
- Вердикты субагентов — **В**; что с ними делать — **Ч**.
- Бриф, выборочная перепроверка — **Д**.

## Где будет реализовано

- `.claude/agents/<имя>.md` — шесть файлов с frontmatter (`tools`, хуки) и брифом.
- Карта AGENTS.md — когда какой субагент предлагать.
- CI — по [28](28-hosting-ci-git.md).
