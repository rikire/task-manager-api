# 24. Планирование и трекинг

**Статус:** принято 2026-10-06, человек; дополнено 2026-10-07 (владелец): статусы и связь роадмап ↔ изменения
проверяются скриптом, порядок изменений — тоже (изменение `finish-init`, FAIL-005). **Область:** 2 «Планирование и трекинг».

## Потребность

Нужно знать, что делаем, в каком порядке и что сознательно не делаем; видеть реальный прогресс, а
не отметки агента; оценивать объём работы, не полагаясь на сроки, которые агент выдумывает; не давать
скоупу расползаться посреди работы.

## Варианты

- **План:** файл роадмапа / внешний трекер / трекер с графом зависимостей (Beads, Backlog.md).
- **Трекинг:** галочки, которые ставит агент (договорённость) / статусы, вычисленные из фактов.
- **Оценка:** сроки от агента / объём в счётных единицах / скорость по собственной истории
  (пропускная способность, Monte Carlo).
- **Скоуп:** явный список «вне рамок»; правило, куда идут новые идеи.

## Решение

### 1. Стратегический план — `docs/roadmap.md`

На русском, для человека ([23](23-documentation.md)):
- цель и скоуп;
- **что вне рамок** — явным списком;
- упорядоченный список запланированных изменений (вертикальных срезов, [02](02-sdd-framework.md))
  с приоритетом;
- вехи — набор изменений, после которого что-то работает целиком и проверяется тестами.

Агент предлагает, человек утверждает.

### 2. Приоритеты

MoSCoW по-русски: «обязательно / желательно / если успеем / не делаем». Документ русский, поэтому
конфликта с английскими MUST / SHOULD из [08](08-normative-descriptive.md) нет.

### 3. Связь стратегии и тактики

- Тактика — `tasks.md` изменения OpenSpec ([07](07-requirements-intent.md)). Каждая задача — на один
  заход и с проверкой: какой тест или команда подтверждает, что задача сделана.
- Каждая строка роадмапа ссылается на изменение по имени (имя папки в `openspec/changes/` или в
  архиве); в `proposal.md` изменения есть поле `Roadmap:` со ссылкой на строку роадмапа.
- Скрипт (`make roadmap-check`: pre-commit, Stop-хук, CI) проверяет связь в обе стороны: у каждого
  изменения есть строка в роадмапе, каждая строка «в работе» или «в архиве» ведёт на существующее
  изменение.
- Порядок (добавлено 2026-10-07, владелец, `FAIL-005`): изменение нельзя начать, пока выше в роадмапе
  есть незаархивированное изменение с приоритетом «обязательно»; проверяет тот же скрипт.

### 4. Трекинг из фактов

- Статус изменения в роадмапе (запланировано / в работе / в архиве) генерирует скрипт по
  `openspec/changes/` и архиву.
- Прогресс внутри изменения: галочки в `tasks.md` — договорённость; объективный прогресс — матрица
  трассировки ([09](09-traceability.md)): какие сценарии покрыты зелёными тестами.
- Отдельный трекер задач не нужен.

### 5. Оценка объёма

- Агент не называет сроки в часах и днях без опоры на историю.
- Объём — в счётных единицах: изменения, сценарии, задачи.
- Когда накопится история, скрипт по git считает пропускную способность (сколько изменений и задач
  закрывается за день), и прогноз даётся диапазоном. Monte Carlo не используем.

### 6. Скоуп

- Новая идея посреди работы не попадает в текущее изменение (стоп-триггер 3,
  [13](13-authority.md)): агент записывает её в роадмап кандидатом с приоритетом или в реестр
  улучшений `IMP` ([10](10-debt-polish-headroom.md)); решает человек.
- «Вне рамок» — в роадмапе и в каждом proposal ([07](07-requirements-intent.md)).

### 7. Внешний дедлайн

По запросу человека в роадмапе проводится линия отсечения по приоритетам: что точно успевается, что
выпадает.

## Обоснование

- Ощущение скорости с ИИ расходится с измерением (METR: на 19% медленнее при ощущении ускорения на
  20%); агенты переоценивают своё время; без истории честный ответ — число задач
  ([ч.4 §6](research/report/04-requirements-planning.md), [ч.3 п.10](research/report/03-weaknesses.md)).
- Прогресс отмечает агент — договорённость; гарантию даёт сверка с фактами
  ([ч.4 §7](research/report/04-requirements-planning.md)).
- Для одного разработчика достаточно роадмапа со скоупом и «вне рамок» плюс задач на изменение;
  трекеры с графом зависимостей окупаются при многих задачах с блокерами; Monte Carlo — при внешнем
  дедлайне и десятках закрытых задач ([ч.4 §6–7](research/report/04-requirements-planning.md)).
- Связь роадмапа с изменениями в обе стороны — решение человека.

## Гарантия

Внедрено 2026-10-07 (изменение `finish-init`): `scripts/roadmap.py` генерирует статусы роадмапа из
изменений OpenSpec, `make roadmap-check` (pre-commit, Stop-хук, CI) проверяет, что статус в ячейке —
«запланировано», «в работе» или «в архиве» и совпадает с фактом, связь строк и изменений в обе стороны
и порядок изменений; счётчик `N/M` (отмечено / всего задач в `tasks.md`) пишет генератор, проверка его
не сверяет, чтобы отметка задачи не валила Stop-хук. Скрипт пропускной способности (§5) и матрица
трассировки не внедрены ([34](34-core-vs-roadmap.md) §4).

- Статусы в роадмапе, связь роадмап ↔ изменения, порядок — **Гф** (скрипт, CI); прогресс по матрице —
  **Д** до внедрения матрицы.
- Галочки в `tasks.md`, «без сроков», запись новых идей — **Д**; приоритеты и отсечение — **Ч**.

## Где будет реализовано

- `docs/roadmap.md` (генерируемая секция статусов).
- `openspec/config.yaml` → `rules.proposal`: поле `Roadmap:`; `rules.tasks`: проверка у каждой задачи.
- Скрипты: статусы роадмапа и связь роадмап ↔ изменения — внедрено (`scripts/roadmap.py`,
  `make roadmap-check`); пропускная способность — не внедрено.
- AGENTS.md: «без сроков без истории», «новая идея — в роадмап или IMP».
