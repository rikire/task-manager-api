# 02. SDD-фреймворк

**Статус:** принято 2026-10-05, человек. **Область:** 1 «Намерение и требования», частично
2 «Планирование и трекинг».

## Потребность

Нужен способ фиксировать намерение и требования до кода и сохранять их между сессиями агента, не
утонув в markdown. SDD (spec-driven development) — подход, при котором до кода пишется спецификация,
и агент реализует по ней.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Без фреймворка: plan mode + интервью → SPEC.md | минимум текста и зависимостей | нет живой спеки, структуру придумываем сами |
| **OpenSpec** | главная спека живёт и обновляется дельтами; низкие–средние накладные расходы; нужен только Node | ещё один слой markdown; проверки внутри цикла почти нет |
| Superpowers (набор скиллов: brainstorm → plan → TDD → review) | встроены TDD и ревью | спека выбрасывается после задачи; много субагентов и токенов; пересекается с нашей проверкой |
| GitHub Spec Kit | самый известный, есть сверка кода со спекой (`converge`) | тяжёлый: Python/uv, много markdown; в замере Scott Logic (один проект) — 3,5 ч ревью markdown на фичу против 15 мин без SDD |
| cc-sdd (в стиле AWS Kiro) | встроены TDD и независимый ревьюер | маленькое сообщество, средне-высокие накладные расходы |

## Решение

**OpenSpec** (v1.14.0 на момент решения).

### Как устроен OpenSpec

- `openspec/specs/` — главная спека: как система ведёт себя сейчас.
- `openspec/changes/<имя>/` — **изменение**: proposal (зачем и что), дельта спеки (какие требования
  добавлены, изменены, удалены), задачи (`tasks.md`), при необходимости `design.md`. Состав
  изменения — [07 §4](07-requirements-intent.md).
- Цикл: `/opsx:propose` (создать изменение) → `/opsx:apply` (реализовать задачи) → `/opsx:archive`
  (влить дельту в главную спеку, перенести изменение в архив). Команды вызываются в Claude Code как
  `/opsx:<команда>`.

### Как используем

- **Единица работы:** одно изменение OpenSpec = один **вертикальный срез** — одно наблюдаемое
  поведение сквозь все слои (маршрут, логика, хранение, тесты), которое можно прочитать и понять за
  один заход. Не эндпоинт и не модуль целиком. Задачи — пункты `tasks.md` внутри изменения.
- **Инициализация:** `openspec init --tools claude,agents` — скиллы и команды для Claude Code и для
  инструментов, читающих AGENTS.md.
- **Профиль команд:** `custom` = базовый набор (propose, explore, apply, update, sync, archive) +
  **continue** (артефакты изменения создаются по одному, человек читает каждый перед следующим) +
  **verify** (сверка реализации со спекой). Поведение continue и verify — по документации OpenSpec,
  проверить при установке; от continue зависит приёмка намерения в [07 §6](07-requirements-intent.md).
- **Доставка команд:** и скиллы, и slash-команды; явный вызов `/opsx:*` надёжнее, чем автовызов
  скилла моделью.
- **Схема артефактов:** стандартная `spec-driven`; свою (форк схемы) делаем, только если её потребуют
  решения по тестам или требованиям.
- **Установка:** человеку после `git clone` должно хватать минимума действий. Версия OpenSpec
  закрепляется в репозитории и ставится командой bootstrap. Механизм — [29](29-environment.md).
- **Телеметрия OpenSpec выключена:** у пользователя — `openspec config set telemetry.enabled false`;
  для проекта по умолчанию — переменная `OPENSPEC_TELEMETRY=0`, которую задаёт окружение проекта
  ([29](29-environment.md)).
- **Язык артефактов** (`--language`) — [23](23-documentation.md).

## Обоснование

- Контролируемых сравнений SDD с итеративной работой нет; главная цена SDD для соло-разработчика —
  чтение markdown; лёгкие варианты (дельта-спеки OpenSpec) нацелены на её снижение
  ([ч.1 §1.3, «Что это значит для соло»](research/report/01-landscape-sdd.md)).
- По классификации Böckeler (Thoughtworks) OpenSpec — spec-anchored: спека не выбрасывается после
  задачи, а живёт и обновляется дельтами, поэтому служит и требованиями, и памятью между сессиями
  ([ч.1](research/report/01-landscape-sdd.md)).
- Встроенную проверку других фреймворков (Superpowers, cc-sdd) не берём: проверка строится отдельно,
  по своим правилам с гарантиями ([01](01-process-frame.md), область 6).
- Маленькие порции работы поддержаны несколькими линиями данных
  ([ч.2 §3.1](research/report/02-evidence.md)); вертикальный срез держит дифф читаемым (область 7).
- Скилл, который модель должна вызвать сама, без явной инструкции срабатывал в 53% случаев (эвал
  Vercel, вендор) ([ч.6](research/report/06-context-security-docs.md)).

## Гарантия

- Наличие и структура артефактов изменения — **Гф** (`openspec validate`, проверки в CI —
  [04](04-definition-of-done.md), [07](07-requirements-intent.md)).
- Качество спеки и соответствие ей кода — **Ч**; `verify` — **В**, вспомогательная.
- Размер «вертикальный срез» — **Д**; предупреждение о размере диффа — [18](18-human-comprehension.md).

## Где будет реализовано

- `openspec/` (config.yaml, specs/, changes/), `.claude/skills/openspec-*`, `.claude/commands/opsx/`,
  `.agents/skills/openspec-*` — генерируются `openspec init`.
- Закрепление версии и bootstrap — по [29](29-environment.md).
- Правила для артефактов (`rules` в `openspec/config.yaml`) — по решениям
  [07](07-requirements-intent.md), [12](12-adr.md) и [23](23-documentation.md).
