# 08. Нормативное и описательное

**Статус:** принято 2026-10-05, человек. **Область:** 1 «Намерение и требования».

## Потребность

Агент превращает описательную фразу или побочный эффект решения в правило и дальше на него опирается.
Пример из практики: из фразы «без JavaScript форма остаётся обычным textarea» в описании фичи агент
вывел запрет на JavaScript во всём проекте, хотя в требованиях и ADR такого не было. Нужно, чтобы
правило (норма) отличалось от описания и у каждого правила был проверяемый источник.

## Варианты

- Лексическая маркировка нормы: по BCP 14 (RFC 2119 + RFC 8174) слова MUST, SHALL, SHOULD, MAY
  нормативны только заглавными буквами.
- Структурное разделение: нормы только в определённых местах, остальное — описание.
- Поле `Source:` у каждого правила + проверка в CI.
- Инструкция «цитируй источник ограничения».
- Перенос машинно проверяемых норм в линтеры, тесты, хуки.
- Инструменты трассировки требований (Doorstop, StrictDoc) — избыточны для малого проекта.

## Решение

1. **Нормы живут только в нормативных местах:**
   - требования в спеках (`SHALL`);
   - раздел «Decision and rationale» в ADR ([12](12-adr.md)); остальные разделы ADR — описательные;
   - раздел правил в AGENTS.md;
   - `.claude/rules/`;
   - документы решений процесса.

   Всё остальное — описательное: `design.md` вне пометок решений (`Scope:` / `ADR:`,
   [07 §4](07-requirements-intent.md)), описания, README, комментарии в коде. **Список открыт:**
   новый тип артефакта явно объявляется нормативным или описательным в реестре документов
   ([23](23-documentation.md)); проверки берут список
   нормативных мест из реестра. Список сверяется в вопросе №31 «Финальная сверка».
2. **Лексика:** MUST, SHALL, SHOULD, MAY заглавными — только в нормативных местах английских
   документов; проверка (pre-commit и CI) ищет их вне нормативных мест. Приоритеты в планировании (например, MoSCoW) записываются нотацией, не
   совпадающей с этими словами, иначе Must и Should из MoSCoW сработали бы как нормы; формат —
   [24 §2](24-planning-tracking.md).
3. **У каждого правила вне спек и ADR — `Source:`:** ссылка на ID требования, ADR, документ
   решения или запись журнала сбоев (`FAIL-…`, [22](22-process-learning.md)). Примеры: `Source: R-CART-add-to-cart`, `Source: ADR-0004-error-format`,
   `Source: docs/pre-init/13-authority.md`. CI проверяет, что ссылка ведёт в существующий файл или ID
   (форматы ID — [09](09-traceability.md)). Требования спек и решения ADR — первоисточники, их
   принимает человек. `Source:` заодно отвечает на вопрос «какую потребность закрывает это правило».
4. **Нет источника — нет ограничения.** Опираясь на ограничение, агент цитирует его `Source:`.
   Ограничение без источника не существует: агент спрашивает человека, а не следует ему.
5. **У нормы — «почему» и границы применения.** Пример: «Не мокать тестируемый модуль — иначе тест
   проверяет мок. Не относится к внешним HTTP-сервисам».
6. **Машинно проверяемая норма уходит в линтер, тест или хук** (лестница из
   [01](01-process-frame.md)); текстовая норма — только для того, что машиной не выразить.

## Обоснование

- Прямых исследований эффекта нет; задокументирован случай, когда агент принял описание
  существующих классов за спецификацию (Böckeler, Thoughtworks); вендор предупреждает, что новые
  модели Claude сильнее реагируют на текст инструкций и могут применять его шире задуманного
  ([ч.4 §4](research/report/04-requirements-planning.md), [ч.3 п.13](research/report/03-weaknesses.md)).
- RFC 8174: ключевые слова нормативны только заглавными; SDD-фреймворки, включая OpenSpec, этим
  пользуются ([ч.4 §4](research/report/04-requirements-planning.md)).
- Готового инструмента для источников правил нет; минимум — нормативная секция с `Source:` и скрипт
  в CI; смысловую ошибку ловит человек, если агент обязан цитировать источник
  ([ч.4 §4](research/report/04-requirements-planning.md)).
- Сбой наблюдался на практике (пример выше) — механизм вводится по пятому принципу
  ([01](01-process-frame.md)).

## Гарантия

- Заглавные ключевые слова вне нормативных мест, наличие и существование `Source:` — **Гф** (CI).
- «Нет источника — нет ограничения», «почему» и границы — **Д**; проверяет человек при ревью (**Ч**).
- Вывод агентом правила из описания детерминированно не закрывается.

## Где будет реализовано

- Скрипт проверки нормативной лексики и `Source:` — в pre-commit и CI.
- Реестр документов с пометкой «нормативный / описательный» — по [23](23-documentation.md).
- Правило «нет источника — нет ограничения» — в AGENTS.md.
- `openspec/config.yaml` → `rules`: заглавные ключевые слова только в требованиях.
