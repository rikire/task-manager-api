# 11. Проектирование архитектуры

**Статус:** принято 2026-10-05, человек. **Область:** 3 «Архитектура и решения».

## Потребность

Агент переусложняет или не продумывает структуру, изобретает своё вместо проверенных паттернов,
принимает решения без опоры на требования и тихо отходит от принятой архитектуры между сессиями.
Нужен лёгкий процесс проектирования, где у каждого шага есть смысл, а не тяжёлая методология.

## Опора на теорию

- **Архитектурные драйверы** — то, от чего отталкивается проектирование (SEI: Bass, Clements, Kazman
  «Software Architecture in Practice»; Cervantes, Kazman — метод ADD 3.0, Attribute-Driven Design):
  цель проектирования, основные функциональные требования, сценарии атрибутов качества с измеримой
  мерой (источник → стимул → артефакт → окружение → реакция → мера), ограничения, сквозные заботы.
- **Итеративность:** ADD 3.0 — цикл «драйверы итерации → выбор паттернов и тактик → элементы и
  интерфейсы → виды и решения → анализ»; усилия на архитектуру пропорциональны риску (Fairbanks
  «Just Enough Software Architecture»).
- **Только нужное:** YAGNI, KISS; необратимое решение откладывается до «последнего ответственного
  момента», обратимые принимаются быстро.
- **Компромиссы:** «всё в архитектуре — компромисс», «почему важнее, чем как» (Richards, Ford
  «Fundamentals of Software Architecture»); метод ATAM (SEI, оценка архитектуры по компромиссам) —
  точки чувствительности (решение заметно влияет на один атрибут) и точки компромисса (улучшает один
  атрибут за счёт другого).
- **Готовые решения:** тактики SEI по атрибутам качества; стили (слои, hexagonal, clean); паттерны
  Fowler «Patterns of Enterprise Application Architecture» (PoEAA), Evans «Domain-Driven Design»
  (DDD), Hohpe, Woolf «Enterprise Integration Patterns» (EIP).
- **Принципы:** сокрытие информации (Parnas), низкая связанность и высокая связность, разделение
  ответственности, SOLID, правило зависимостей (зависимости направлены к домену — Martin «Clean
  Architecture»).
- **Виды архитектуры:** статический (из чего состоит код), динамический (что происходит при
  выполнении), физический (куда развёрнуто) — SEI Views & Beyond; вид существует ради заботы
  конкретного читателя (ISO/IEC/IEEE 42010). Нотация C4: Context → Container → Component → Code +
  Dynamic, Deployment. Каркас документации — arc42 (12 секций).

Из ADD берётся смысловое ядро — драйверы → паттерны и тактики → компромиссы → запись → проверка, —
без документирования каждого шага. Состав arc42, шаги ADD и виды C4 сверены по первоисточникам;
остальные книги — по памяти и используются как индекс в скилле, на решения не влияют.

## Решение

### 1. Артефакты

| Артефакт | Где | Что внутри |
|---|---|---|
| Описание архитектуры | `docs/architecture/README.md` | урезанный arc42 (ниже) |
| Сценарии качества `Q-<ATTR>-<slug>` | `openspec/specs/quality/` (отдельная capability; уникальность слага — внутри неё) как требования со сценариями | атрибут качества с измеримой мерой; дельты, история и трассировка — как у требований `R-` ([09](09-traceability.md)) |
| ADR | `docs/adr/ADR-NNNN-<slug>.md` | архитектурные решения с компромиссами ([12](12-adr.md)) |
| Диаграммы | Mermaid прямо в `docs/architecture/README.md` (GitHub рисует без инструментов) | context, container; runtime и deployment — по необходимости |
| Правила зависимостей | конфиг инструмента (по стеку) + правила `C-ARCH-<slug>` в `.claude/rules/` с `paths` на папки кода | слои, правило зависимостей, отсутствие циклов |
| Локальные решения | `design.md` изменения | решения одного среза ([07 §4](07-requirements-intent.md)) |

Пример сценария качества: `Q-PERF-cart-p95` — «при 100 одновременных запросах (стимул) к API
корзины (артефакт) в штатном режиме (окружение) ответ (реакция) приходит за ≤ 200 мс в 95% случаев
(мера)». Правила [07](07-requirements-intent.md) (ID, сценарий нежелательного поведения) к `Q-`
применяются так же.

Секции `docs/architecture/README.md` (секция без содержания не создаётся):
1. Цели качества — 3–5 приоритетных атрибутов (мини utility tree — дерево приоритетов атрибутов) со
   ссылками на `Q-`.
2. Ограничения — ссылки на `C-`.
3. Контекст — C4 System Context: кто пользуется системой и с чем она связана.
4. Стратегия решения — стиль, таблица стека ([12 §1](12-adr.md)), ключевые решения со ссылками на
   ADR.
5. Строительные блоки — C4 Container / модули, ответственность каждого в одну строку.
6. Runtime — только неочевидные ключевые потоки.
7. Deployment — если процессов больше одного.
8. **Сквозные концепции (обязательна)** — обработка ошибок, валидация, транзакции, логирование,
   конфигурация, безопасность ([14 §4](14-code-security.md)): здесь агенты чаще всего изобретают
   каждый раз своё.
9. Ссылки — ADR, реестр долга и улучшений, глоссарий (когда появится, [34](34-core-vs-roadmap.md)).

Диаграмма существует, только если у неё есть читатель и забота; у каждой — подпись, зачем она.

### 2. Процессы

**А. Старт архитектуры (один раз).** Первое изменение OpenSpec после того, как приняты первичные
требования; запускает человек. Шаги: собрать драйверы (главные `R-`, `Q-` с мерой, `C-`); выбрать
стиль и структуру модулей — 2–3 варианта с компромиссами, выбирает человек → ADR; записать правила
зависимостей; написать `docs/architecture/README.md` (контекст, container, сквозные концепции).

**Б. Проверка значимости в каждом изменении.** На шаге design — в `design.md`, а если его нет, в
`proposal.md` — агент проходит чек-лист «архитектурно значимо?»: новый модуль или граница; схема
данных; контракт API; новая зависимость, которую трудно заменить; новая сквозная концепция; влияние
на сценарий `Q-`; трудно откатить. Этот чек-лист — часть поводов для ADR; полный список —
[12 §1](12-adr.md).
- **Нет** — решения локальные, в `design.md`.
- **Да** — мини-цикл: драйверы → известные паттерны и тактики → 2+ варианта с компромиссами →
  выбирает человек → ADR → **в том же изменении** обновить описание архитектуры, диаграммы и правила
  зависимостей.
- Решение без драйвера (`R-`, `Q-`, `C-`) не принимается.

**В. Контроль дрейфа.** Правила зависимостей в CI; проверка ссылок в документах; проверка, что
новый модуль верхнего уровня отражён в «Строительных блоках». Реализуемость последней проверки
решается при инициализации; до тех пор это договорённость.

### 3. Знания агента

Уровень, на котором агент по умолчанию применяет теорию, неизвестен: текст может звучать уверенно, а
применение — быть непоследовательным (слабая архитектура и переусложнение — подтверждённые слабости).
Поэтому знания **не полагаются на память агента**:

- **Скилл `architecture`.** Вызывает агент на шаге design при «да» по чек-листу значимости, или
  человек командой `/architecture`; строка в карте AGENTS.md ([03](03-agent-instructions.md)).
  Содержит операциональные определения и чек-листы, а не пересказ книг:
  - типы драйверов, формат сценария `Q-`;
  - чек-лист значимости;
  - метод компромиссов: таблица «варианты × атрибуты качества», точки компромисса и
    чувствительности, «почему выбрано»;
  - индекс готовых решений с «когда применять»: тактики по атрибутам, стили, паттерны PoEAA / DDD /
    EIP;
  - принципы с проверочными вопросами (что значит нарушение принципа единственной ответственности,
    признаки низкой связности и т.п.);
  - какие диаграммы для какой заботы;
  - типичные ошибки агента: обёртки вокруг фреймворка, абстракция без второй реализации, непрошеная
    функциональность, решение без драйвера.
- **Ссылки обязательны:** в варианте и решении агент называет применённый принцип, тактику или
  паттерн и почему; «так лучше» без обоснования не принимается.
- **Правила `C-ARCH-<slug>`** — короткие правила слоёв с «почему» и `Source:`.
- **`docs/architecture/README.md`** — знание о нашей системе.
- **Проверка уровня — на своих задачах:** несколько eval-кейсов архитектурных решений с прогоном со
  скиллом и без ([22 §3](22-process-learning.md));
  итоговая проверка — ревью человеком.

**Шлюз простоты** (правило `C-ARCH`): без собственных обёрток вокруг фреймворка; новая абстракция —
только при второй реальной реализации или по сработавшему триггеру `IMP`
([10](10-debt-polish-headroom.md)). Новые зависимости — только с одобрения человека
([13](13-authority.md)).

### Не делаем

Полную процедуру ADD с документированием шагов, воркшопы ATAM, большое дерево приоритетов, Component
и Code диаграммы без необходимости, Structurizr.

## Обоснование

- Агент генерирует варианты, выбор и приёмка — за человеком; ревьюер без фильтра провоцирует
  переусложнение; минимум с гарантией — 3–6 правил зависимостей
  ([ч.5 «Проектирование архитектуры»](research/report/05-architecture-testing-verification.md)).
- Слабая архитектура и дрейф — подтверждённая слабость (деградация измерена; дрейф между сессиями —
  без данных) ([ч.3 п.8](research/report/03-weaknesses.md)).
- «Если у задачи есть название, её уже решали»: секция известных решений, одобрение зависимостей
  ([ч.4 §10](research/report/04-requirements-planning.md)).
- Источники теории, сверенные по первоисточнику: [arc42](https://docs.arc42.org/home/),
  [C4](https://c4model.com/), [ADD 3.0](https://oreilly.com/library/view/designing-software-architectures/9780134390857).

## Гарантия

- Правила зависимостей — **Г**; связи ADR, `Q-` ↔ тесты, ссылки, соответствие модулям — **Гф**.
