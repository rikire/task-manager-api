# To be discussed

Очередь вопросов, которые нужно решить до инициализации проекта.

**Порядок работы.** Берём пункт → агент описывает его и предлагает вариант → обсуждаем и согласуем →
агент пишет документ решения `docs/pre-init/NN-<тема>.md` (формат — в
[docs/pre-init/README.md](README.md)) → пункт помечается «решено» со ссылкой на
документ. Когда решены все пункты, по документам инициализируем репозиторий и настраиваем harness,
процессы и документацию.

**Номера.** Номер вопроса в очереди и номер документа решения могут не совпадать: документы
нумеруются в порядке принятия решений (например, вопрос №32 → `19-agent-writing.md`).

**Статусы:** `открыт` · `обсуждается` · `решено → NN-<тема>.md` · `отложен` (с причиной).

Рекомендации ниже — из исследования ([report.md](research/report.md)), не решения.
Отчёт сам оговаривает: контролируемых сравнений процессов нет, механизмы выбираются по тому,
исполняется ли проверка и сколько стоит внимания человека.

Обозначения силы механизма: **Г** — гарантия (исполняется вне модели), **Гф** — гарантия формы
(проверяется наличие и структура, не смысл), **В** — вероятностная проверка (LLM), **Д** —
договорённость, **Ч** — суждение человека.

## 01. Каркас процесса
- **Вопрос:** на какие области делим процесс и как описываем каждую.
- **Рекомендация:** вариант D (области вокруг узких мест: намерение, контекст, ограничения, проверка,
  обучение процесса, понимание кода) + классификация механизмов по B (Г / Гф / В / Д / Ч) + лёгкая
  часть C для требований и планирования.
- **Решить:** набор областей; шаблон описания области; куда ложатся остальные пункты; разделение
  «продукт (спеки, дизайн, контракт API) / процесс»; бюджет на процесс — какую долю времени он может
  занимать, чтобы не съесть саму работу.
- **Источник:** report.md, «Итог, а)»; ч.1.
- **Статус:** решено → [01-process-frame.md](01-process-frame.md)

## 02. SDD-фреймворк
- **Вопрос:** нужен ли SDD и какой.
- **Рекомендация:** только лёгкий вариант — дельта-спеки (OpenSpec), plan mode + стандарты или

- **Решить:** фреймворк или без него; какие артефакты обязательны; как ставится CLI (глобально или
  зависимостью проекта, закреплённая версия); телеметрия.

- **Статус:** решено → [02-sdd-framework.md](02-sdd-framework.md)

## 03. Инструкции агенту
- **Вопрос:** как устроены AGENTS.md / CLAUDE.md, правила, скиллы.
- **Рекомендация:** короткий файл, написанный человеком, только неочевидное (команды, нестандартные
  правила); без обзора репозитория; правила по путям; индекс скиллов в основном файле (автовызов
  скилла не гарантирован). Сила — Д.
- **Решить:** какой файл основной; бюджет объёма; что идёт в правила по путям, что в скиллы;
  правило «версии, API и флаги проверять по источнику, а не по памяти»; проверка в CI, что пути и
  команды в инструкциях существуют; использовать ли автопамять агента в проекте.
- **Источник:** ч.6 «Контекст агента», «Доставка инструкции».
- **Статус:** решено → [03-agent-instructions.md](03-agent-instructions.md)

## 04. Definition of Done и проверка утверждений
- **Вопрос:** как не принимать «готово» на слово.
- **Рекомендация:** один скрипт проверки = DoD; Stop-хук блокирует завершение, пока он красный; тот
  же скрипт в CI с required checks; три статуса: done (агент) / verified (проверки) / accepted
  (человек). Сила — Г.
- **Решить:** состав DoD; где хранится статус; что проверяет человек при accepted.
- **Источник:** ч.5 «Проверка утверждений агента», «Три состояния»; ч.7 §1.
- **Статус:** решено → [04-definition-of-done.md](04-definition-of-done.md)

## 05. TDD
- **Вопрос:** как обеспечить и сделать проверяемым порядок «тест → код».
- **Рекомендация:** две фазы — человек принимает тесты, затем реализация при тестах только на чтение
  (deny + песочница); порядок виден в коммитах. Сила — Г. TDD-Guard (LLM на каждое действие) — спорно.
- **Решить:** кто пишет и кто принимает тесты; как защищаются тесты; формат коммитов.
- **Источник:** ч.5 «TDD с агентом».
- **Статус:** решено → [05-tdd.md](05-tdd.md)

## 06. Качество тестов
- **Вопрос:** как получить тесты, которые ловят ошибки, а не просто зелёные.
- **Рекомендация:** метод вывода корнер-кейсов (проход по измерениям входа); мутационное тестирование
  на изменённых файлах (Г измерения); без избыточных happy-path; ревьюер-субагент в свежем контексте,
  read-only (В).
- **Решить:** порог мутаций; правила для тестов; когда звать ревьюера.
- **Источник:** ч.5 «Качество тестов»; ч.3 п.4.
- **Из 05:** подробное правило для агента, как писать тесты: метод вывода корнер-кейсов, без
  однотипных happy-path; проверка через мутационное тестирование.
- **Статус:** решено → [06-test-quality.md](06-test-quality.md)

## 08. Нормативное и описательное

## 12. ADR
- **Вопрос:** как записывать архитектурные решения.
- **Рекомендация:** минимальный ADR (MADR или Y-statement) только для дорогих решений; агент пишет

- **Решить:** когда ADR обязателен; формат; где лежат; связь со спеками.
- **Источник:** ч.5 «Архитектурные решения (ADR)»; ч.6 «Согласованность инструкций».

- **Из 07:** критерии «решение архитектурное» (решения из design.md с пометкой `ADR: ADR-NNNN-<slug>`).

## 13. Полномочия человека и агента
- **Вопрос:** что агент решает сам, а что только человек; когда агент останавливается.
- **Рекомендация:** явный список решений человека; наблюдаемые стоп-триггеры; агенту запрещено
  править свои инструкции, хуки и конфигурацию проверок (deny, Г).
- **Решить:** список; триггеры; что под deny; правила честности (возразить один раз с альтернативой,
  называть более простое решение, не скрывать непонимание, отделять факт от допущения) — против
  sycophancy и додумывания.
- **Источник:** ч.5 «Принятие решений»; ч.3 п.14–15.
- **Из 04:** `ask` на git commit / push, `deny` на `--no-verify`.
- **Из 06:** защита порога мутаций и конфигурации тест-раннера от ослабления агентом.
- **Из 09:** deny на правку генерируемого файла матрицы трассировки.
- **Статус:** решено → [13-authority.md](13-authority.md)

## 15. Безопасность работы агента
- **Вопрос:** prompt injection, выдуманные пакеты, секреты, права.
- **Рекомендация:** песочница strict; deny на секреты; lock-файл; задержка (cooldown) на новые пакеты;
  режим прав не выше acceptEdits.
- **Решить:** режим прав; песочница; правила для зависимостей; allowlist частых безопасных команд
  (например, через `/fewer-permission-prompts` по реальной истории).
- **Источник:** ч.6 «Безопасность работы агента».
- **Из 13:** песочница закрывает обход ask/deny через Bash; проект совместим с auto mode,
  bypass запрещён.
- **Статус:** решено → [15-agent-security.md](15-agent-security.md)

  ошибки, не писать своё вместо библиотеки; коммерческий quality gate не нужен.
- **Решить:** набор правил кода; что в хуке после правки, что в CI.
- **Источник:** ч.5 «Качество кода и архитектуры»; ч.3 п.3, 6, 7.
- **Из 09:** раздувание кода, повторы, YAGNI/DRY — детектор дублей, пороги размера и сложности,
  обратная трассировка, мутации, вопрос ревьюера «нужен ли этот код».
