# 05. TDD

**Статус:** принято 2026-10-05, человек; изменено 2026-10-06: коммит на группу задач, защита тестов —
хуком без песочницы. **Область:** 6 «Проверка».

## Потребность

Порядок «тест → код» в инструкции — договорённость, и агенты её нарушают; кроме того, они правят
тесты, чтобы те прошли. Нужно, чтобы тесты задавали поведение до реализации и не менялись под
реализацию.

## Варианты

- **Как обеспечить порядок:** инструкция (Red → Green → Refactor, Kent Beck) / красный вывод в логе /
  пары коммитов `test:` → `feat:` с CI-проверкой «сначала падал, потом прошёл» / TDD-Guard (LLM
  проверяет каждое действие агента) / фазовое разделение с защитой тестов от записи.
- **Кто пишет тесты:** агент, человек принимает / человек.
- **История:** пары коммитов / один зелёный коммит.

## Решение

### Фазы

1. **Тесты (`tests`).** Агент пишет тесты по сценариям спеки и запускает их. Тесты должны падать по
   правильной причине — на проверке результата, а не из-за отсутствующего кода. Например, заглушка
   функции возвращает пустой результат, и тест падает на сравнении, а не на ошибке импорта или
   компиляции. Агент показывает красный вывод. **Человек читает и принимает тесты.**
2. **Реализация (`impl`).** Тесты защищены от правки: хук, который знает текущую фазу, блокирует
   запись в тестовые пути. Агент пишет минимальный код до зелёного. Если агент считает тест
   неверным — **останавливается и спрашивает**, а не правит.
3. **Рефакторинг (`refactor`).** Тесты зелёные и по-прежнему защищены; меняется только структура.
   Если рефакторинг требует правки тестов (например, переименован публичный API), агент просит
   вернуться в фазу `tests`.

**Переключение фаз** ([16 §2](16-guardrails-harness.md)): заблокировать тесты (`impl`, `refactor`)
агент может сам; разблокировать (`tests`) — только с подтверждения человека одним кликом.

Stop-хук в фазе `tests` допускает падение новых и изменённых тестов активного изменения
([04](04-definition-of-done.md)).

### История

**Коммит на группу задач** `tasks.md` внутри ветки изменения, каждый зелёный, после приёмки этой
группы человеком ([04](04-definition-of-done.md)); слияние через rebase сохраняет их все
([28](28-hosting-ci-git.md)) — задача требует мелких коммитов ([31](31-task-requirements.md)). Тесты
группы и код группы — в одном коммите; красный вывод фазы `tests` агент кладёт в сводку для ревью.
Пары коммитов `test:` → `feat:` не используются.

### Исключения из TDD

- Инфраструктура и конфигурация (контейнеры, CI, настройки фреймворка) — проверяются smoke-тестом
  «приложение поднялось».
- Генерируемый код и миграции схемы — проверяются интеграционными тестами на реальной БД после
  применения миграции.
- Рефакторинг вне изменения OpenSpec (без нового поведения) — без фазы 1, при зелёных тестах.

### Не берём

**TDD-Guard** — LLM-вызов на каждую правку и вероятностный вердикт; порядок уже защищён дешевле:
фазы, приёмка тестов человеком, защита тестов от записи.

### Связанное

Как писать тесты, чтобы они покрывали корнер-кейсы, а не плодили однотипные проверки основного
сценария, — [06](06-test-quality.md).

## Обоснование

- Инструкции о TDD — договорённость (Kent Beck; Spec Kit «Article III» — тесты пишутся и
  принимаются человеком до кода)
  ([ч.5 «TDD с агентом»](research/report/05-architecture-testing-verification.md)).
- Бенчмарк ImpossibleBench: агенты модифицируют тесты, чтобы пройти; «stronger models generally
  exhibit higher cheating rates»; доступ к тестам только на чтение снижает проблему
  ([ч.5](research/report/05-architecture-testing-verification.md), [ч.3 п.15](research/report/03-weaknesses.md)).
- Самое дешёвое сочетание с гарантией для малого проекта — фазы с приёмкой тестов и защитой тестов от
  записи; трение (ошибка в тесте возвращает работу к человеку) — нужная точка контроля
  ([ч.5](research/report/05-architecture-testing-verification.md)).
- Данных, что строгий TDD с агентом даёт меньше дефектов, чем тесты после кода, нет; тесты как
  спецификация повышают решаемость задач (2024)
  ([ч.5](research/report/05-architecture-testing-verification.md)).

## Гарантия

- Защита тестов от записи в фазах `impl` и `refactor` — **Г** для встроенных инструментов правки (хук +
  переключатель из [16](16-guardrails-harness.md)); запись через Bash хук ловит по известным формам
  команд — по возможности; список обходов — [16 §4](16-guardrails-harness.md).
- Тесты падают по правильной причине, красный вывод в сводке — **Д**, проверяется чтением.
- Приёмка тестов — **Ч**.
- Порядок «тест → код» в истории git — не гарантируется (тесты и код группы в одном коммите).
