Практическая задача.
Как устроено это задание
В документе одна практическая задача — небольшое приложение.


Ответом на неё будет код:
1. Сделайте задание в публичном Git-репозитории на GitHub или GitLab.
2. В своей копии документа заполните разделы «Ваше решение» и «Ваши контакты» в конце.
3. Откройте доступ к копии на чтение и пришлите ссылку рекрутеру.


Срок сдачи сообщит рекрутер вместе с заданием. Если понимаете, что не успеваете, напишите ему до окончания срока.
Объём. Если вы уже знакомы с Symfony и Docker, обязательная часть займет примерно 6–10 часов чистого времени. Если стек новый — заложите время на чтение документации, это нормально. Аккуратно сделанная база важнее дополнительных фичей. Если не успеваете всё — сделайте стабильно работающий CRUD и чистые миграции, а в README напишите, что не успели.
Вопросы про сроки и формат сдачи задавайте рекрутеру. Если требование можно понять по-разному, ждать ответа не нужно: выберите разумный вариант и опишите его в README. Нам интересно, как вы рассуждаете.


Необходимо разработать небольшой REST API для управления задачами (Task Manager).
Требования


Реализовать API для работы с задачами:
Сущность Task
id
title
description
status (new, in_progress, done, …)
created_at
updated_at
Сущность Status
id
name
title
API


Создать задачу
POST /api/tasks


Тело запроса:
{
  "title": "Подготовить отчет",
  "description": "Отчет по продажам за май"
}




Получить список задач
GET /api/tasks


Поддержать фильтр по статусу:
GET /api/tasks?status=done


Получить задачу
GET /api/tasks/{id}


Удалить задачу
DELETE /api/tasks/{id}


Изменить статус у задачи
PATCH /api/tasks/{id}/status


Тело запроса:
{
  "status": "done"
}


Получить список статусов
GET /api/statuses


Получить статус
GET /api/statuses/{id}


Добавить статус
POST /api/statuses


Тело запроса:
{
  "name": "code_review",
  "title": "Ревью кода"
}


Удалить статус
DELETE /api/statuses/{id}

Что необходимо предоставить
* Ссылку на публичный Git-репозиторий (GitHub или GitLab). Коммитьте по ходу работы небольшими шагами с понятными сообщениями и не объединяйте историю перед отправкой: нам интересно, как вы шли к решению. После того как пришлёте ссылку, не пушьте в основную ветку: мы проверяем коммит, который вы укажете в разделе «Ваше решение». Если захотите что-то поправить, сделайте это в отдельной ветке.
* README.md с разделами:
   * Как запустить: команды от git clone до готового API (в идеале: docker compose up -d, миграции, и по какому адресу слать запросы).
   * Архитектурные решения и компромиссы (3 – 7 пунктов): как вы связали Task и Status, как обработали удаление статуса, почему выбрали именно такую структуру проекта и что сознательно упростили.
   * Что дальше: что вы сделали бы иначе или добавили, будь у вас еще пара дней.
   * Использование ИИ: для чего применяли и как проверяли результат (или «не использовал»).
   * Сколько времени ушло: честная цифра (на оценку не влияет).
* По желанию: коллекцию Postman или curl-примеры запросов, скриншоты или короткое видео работы приложения.
Дополнительные баллы

Любые осмысленные улучшения за рамками базовых требований будут плюсом — главное, кратко обоснуйте их в README.


Про ИИ-ассистенты
Пользоваться Copilot, Cursor, ChatGPT, Claude, Antigravity и другими ассистентами можно — мы в работе тоже ими пользуемся. Важно, чтобы вы понимали каждую строку своего решения и могли объяснить, почему сделали именно так. На следующем этапе мы попросим рассказать о решении и внести в него небольшое изменение (см. «Что будет дальше» в конце документа).
В README коротко напишите, для чего применяли ассистента и как проверяли результат. Например: «сгенерировал заготовку формы и переписал валидацию». Честный ответ оценку не снижает.


На что мы смотрим:


* Проект поднимается строго по README одной-двумя командами (docker compose up) и работает.
* Поведение в неидеальных сценариях: валидация битого JSON, передача несуществующих ID/статусов, удаление статуса, к которому привязаны задачи.
* Чистота кода: читаемость, разделение ответственности (контроллеры не содержат сырой SQL/всю бизнес-логику), типизация.
* Насколько архитектурные решения в коде совпадают с тем, что написано в README.


Делать не нужно: пагинацию, сложную авторизацию или админку, деплой на внешний сервер.

Как вы узнаете результат?
Вернёмся с ответом на почту или в Telegram в течение 3 рабочих дней после того, как вы пришлёте ссылку, — обязательно дадим обратную связь. Если не получите письмо — проверьте папку «Спам» и напишите рекрутеру.
Что будет дальше. Если решение нам подойдёт, мы пригласим вас на созвон. Вы покажете код и работу API и расскажете о своих решениях, а потом вместе с нами внесёте в код небольшое изменение. Работать будете в своём репозитории, в отдельной ветке и в своей IDE. Доработку делаем без ИИ-ассистента. Документацией пользоваться можно. Понадобятся компьютер с запущенным проектом и возможность показать экран. Учить ничего специально не нужно: достаточно хорошо понимать свой код.
